LEC-1: Introduction to DBMS 🔥 CodeHelp

1. What is Data?

  1. Data is a collection of raw, unorganized facts and details like text, observations, figures, symbols, and descriptions of things etc.
    In other words, data does not carry any specific purpose and has no significance by itself.
    Moreover, data is measured in terms of bits and bytes — which are basic units of information in the context of computer storage and processing.
  2. Data can be recorded and doesn’t have any meaning unless processed.

2. Types of Data

  1. Quantitative:
    • Numerical form.
    • Weight, volume, cost of an item.
  2. Qualitative:
    • Descriptive, but not numerical.
    • Name, gender, hair color of a person.

3. What is Information?

  1. Information is processed, organized, and structured data.
  2. It provides context of the data and enables decision making.
  3. Processed data that make sense to us.
  4. Information is extracted from the data, by analyzing and interpreting pieces of data.
  5. Example: You have data of all the people living in your locality. It's Data. When you analyze and interpret the data and come to some conclusion that:
    • There are 100 senior citizens.
    • The sex ratio is 1.1.
    • Newborn babies are 100.
    These are information.

4. Data vs Information

  1. Data is a collection of facts, while information puts those facts into context.
  2. While data is raw and unorganized, information is organized.
  3. Data points are individual and sometimes unrelated. Information maps out that data to provide a big-picture view of how it all fits together.
  4. Data, on its own, is meaningless. When it’s analyzed and interpreted, it becomes meaningful information.
  5. Data does not depend on information; however, information depends on data.
  6. Data typically comes in the form of graphs, numbers, figures, or statistics. Information is typically presented through words, language, thoughts, and ideas.
  7. Data isn’t sufficient for decision-making, but you can make decisions based on information.

5. What is Database?

  1. Database is an electronic place/system where data is stored in a way that it can be easily accessed, managed, and updated.
  2. To make real use of Data, we need Database management systems (DBMS).

6. What is DBMS?

  1. A database-management system (DBMS) is a collection of interrelated data and a set of programs to access those data. The collection of data, usually referred to as the database, contains information relevant to an enterprise. The primary goal of a DBMS is to provide a way to store and retrieve database information that is both convenient and efficient.
  2. A DBMS is the database itself, along with all the software and functionality. It is used to perform different operations, like addition, access, updating, and deletion of the data.

8. DBMS vs File Systems

  1. File-processing systems have major disadvantages:
    1. Data Redundancy and Inconsistency: Multiple files contain duplicated info, wasting space and falling out of sync.
    2. Difficulty in Accessing Data: Requires writing specialized application routines for every ad-hoc query.
    3. Data Isolation: Data scattered across multiple files in varying formats.
    4. Integrity Problems: Difficult to enforce consistency constraints across isolated operating system files.
    5. Atomicity Problems: A computer crash during execution leaves partial file updates, causing corruption.
    6. Concurrent-Access Anomalies: Multiple programs updating records concurrently without isolation lead to race conditions.
    7. Security Problems: Difficult to provide granular role-based authorization to specific subsets of data.
  2. The above 7 disadvantages are also the 7 Core Advantages of DBMS (The answer to "Why use DBMS?").

LEC-2: DBMS Architecture 🔥 CodeHelp

1. View of Data (Three Schema Architecture)

  1. The major purpose of DBMS is to provide users with an abstract view of the data. That is, the system hides certain details of how the data is stored and maintained.
  2. To simplify user interaction with the system, abstraction is applied through several levels of abstraction.
  3. The main objective of three level architecture is to enable multiple users to access the same data with a personalized view while storing the underlying data only once.
  4. Physical level / Internal level:
    1. The lowest level of abstraction describes how the data are stored.
    2. Low-level data structures used.
    3. Has Physical schema which describes physical storage structure of DB.
    4. Talks about: Storage allocation (B+ trees, N-ary trees), Data compression & encryption.
    5. Goal: Define algorithms that allow efficient access to data.
  5. Logical level / Conceptual level:
    1. Describes what data are stored in DB, and what relationships exist among those data.
    2. User at logical level does not need to be aware of physical-level structures.
    3. DBA, who must decide what information to keep in DB, uses logical level.
    4. Goal: Ease of use.
  6. View level / External level:
    1. Highest level of abstraction; provides different view to different end-users.
    2. Each view schema describes the database part a particular user group is interested in and hides the rest.
    3. Subschema defines personalized views and provides security mechanisms.

  1. The overall design of the DB is called the DB schema.
  2. Schema is structural description of data. Schema doesn’t change frequently. Data may change frequently.

  • Functions: Schema definition, storage structures, authorization control, routine maintenance (backups, security patches, upgrades).

LEC-2: 2-Tier & 3-Tier Architectures 🔥 CodeHelp

b. T2 Architecture (Two-Tier)

  • App is partitioned into 2 components: Client machine and Server machine.
  • Client machine invokes DB functionality directly at server end through query language statements via ODBC/JDBC.

c. T3 Architecture (Three-Tier)

  • App is partitioned into 3 logical components:
    1. Client Machine: Pure frontend (browser or app), contains zero direct DB calls.
    2. Application Server: Communicates with client, holds all business logic.
    3. Database Server: Handles storage, queries, and transactions.
  • Why T3 is best for WWW applications:
    • Scalability: Scalable due to distributed application servers.
    • Data Integrity: App server acts as middle layer minimizing data corruption.
    • Security: Client cannot directly touch the DB.

LEC-3: Entity-Relationship Model 🔥 CodeHelp

1. ER Model Concept

  • High-level conceptual model representing the real world as basic objects called entities and relationships among them.
  • Graphical representation is the ER diagram, which acts as the blueprint of the DB.

2. Entity & Entity Sets

  • Entity: A "thing" or "object" in the real world distinguishable from all others (e.g. Student, Customer).
  • Strong Entity: Can be uniquely identified on its own by a Primary Key attribute.
  • Weak Entity: Cannot be uniquely identified on its own; depends on an identifying strong entity for existence (e.g. `Payment` depends on `Loan`).
  • Entity Set: Set of entities of the same type sharing the same properties (e.g., all Students).

3. Attributes & Attribute Types

  • Simple: Cannot be divided further (e.g., Roll number, Account number).
  • Composite: Can be divided into subparts (e.g., `Name` into `First_Name`, `Last_Name`; `Address` into `Street`, `City`, `PIN`).
  • Single-valued: Exactly one value (e.g., `Student_ID`).
  • Multi-valued: Can have multiple values (e.g., `Phone_Number`, `Dependent_Name`).
  • Derived: Derived from other related attributes (e.g., `Age` from `DOB`).

LEC-3: Relationships & Cardinality 🔥 CodeHelp

4. NULL Values

  • Indicates "not applicable" (e.g. Person has no middle name) or "unknown" (missing entry or not yet determined).

5. Relationships & Degree

  • Relationship: Association among two or more entities.
  • Degree of Relationship:
    • Unary: 1 entity participates (e.g. `Employee manages Employee`).
    • Binary: 2 entities participate (e.g. `Student takes Course`) — Most common!
    • Ternary: 3 entities participate (e.g. `Employee works-on Branch for Job`).

6. Cardinality Ratios (Mapping Constraints)

  • One-to-One (1:1): Citizen ↔ Aadhar Card.
  • One-to-Many (1:N): Citizen ↔ Vehicles.
  • Many-to-One (N:1): Course ↔ Professor.
  • Many-to-Many (M:N): Customer ↔ Products; Student ↔ Courses.

7. Participation Constraints

  • Partial Participation: Not all entities are involved in the relationship instance.
  • Total Participation: Every entity must be involved in at least one relationship instance (represented by double line). Weak entities always have total participation.

LEC-4: Extended ER Features (EER) 🔥 CodeHelp

1. Specialisation (Top-Down Approach)

  • Splitting up an entity set into distinctive sub-entity sets based on functionalities and specialities.
  • Example: `Person` (superclass) divided into `Customer`, `Student`, `Employee` (subclasses).
  • Connected via "is-a" relationship depicted by a triangle pointing up to superclass.

2. Generalisation (Bottom-Up Approach)

  • Reverse of Specialisation: Identifies common attributes across entities and synthesizes a generalized superclass.
  • Example: `Car`, `Jeep`, and `Bus` generalized to `Vehicle`. Eliminates data repetition.

3. Inheritance

  • Attribute Inheritance: Subclasses inherit all attributes of their superclass.
  • Participation Inheritance: If parent entity participates in a relationship, child entity sets participate as well.

4. Aggregation

  • Treats a relationship among entities as a higher-level abstract entity so it can participate in other relationships.
  • Prevents redundant multi-way relationships.

LEC-7: Relational Model & Relational Keys 🔥 CodeHelp

1. Relational Model Terminology

  • Organizes data in relations (tables).
  • Tuple: A single row representing a unique record.
  • Columns: Attributes with permitted values (domain).
  • Degree: Number of attributes/columns in a table.
  • Cardinality: Total number of rows/tuples in a table.
  • Values must be atomic (indivisible). Row and column order has no significance.

2. Relational Model Keys

  • Super Key (SK): Any set of attributes that uniquely identifies each tuple.
  • Candidate Key (CK): Minimum subset of super key with no redundant attributes. Cannot be NULL.
  • Primary Key (PK): Selected out of candidate keys; has least attributes. Unique and NOT NULL.
  • Alternate Key (AK): All candidate keys except the chosen primary key ($AK = CK \setminus \{PK\}$).
  • Foreign Key (FK): Creates relations between two tables. An attribute in child table referencing primary key of parent table.
  • Composite Key: Primary key formed using at least 2 attributes.
  • Compound Key: Key formed using at least 2 foreign keys.
  • Surrogate Key: Synthetic primary key automatically generated by DB (e.g. Auto-increment ID).

3. Integrity Constraints

  • Domain Constraints: Restricts data types and valid range of values.
  • Entity Constraints: Every relation must have a Primary Key, and PK cannot be NULL.

LEC-7: Referential & Key Constraints 🔥 CodeHelp

4. Referential Constraints

  • Specified between two relations to maintain consistency among tuples.
  • Values appearing in FK of referencing table must appear in PK of referenced table or be explicitly `NULL`.
  • Prevents orphaned records in child tables.

5. Six Key Constraints in DBMS

  1. NOT NULL: Restricts attribute from having NULL values. Ensures mandatory presence of data.
  2. UNIQUE: Ensures all values in a column are distinct from each other.
  3. DEFAULT: Sets a default fallback value if none is specified during insertion.
  4. CHECK: Validates condition before permitting CRUD operations (e.g., `CHECK (age > 18)`).
  5. PRIMARY KEY: Uniquely identifies entity tuples; enforces both `UNIQUE` and `NOT NULL`.
  6. FOREIGN KEY: Links child table to parent table, preventing actions that destroy connection integrity.

LEC-8: Transform ER Model to Relational Model 🔥 CodeHelp

Mapping Rules:

  1. Strong Entity: Becomes an individual table. Entity name → table name, attributes → columns, PK → table PK.
  2. Weak Entity: Forms a table with all weak attributes + PK of owner strong entity added as FK. PK is composite: {FK + Partial Discriminator Key}.
  3. Single-Valued Attributes: Represented as columns directly in relations.
  4. Composite Attributes: Flattened into separate individual columns (e.g., Address → street, city, pin). Parent attribute ignored.
  5. Multivalued Attributes: Must form a new table!
    • Columns: PK of owner entity (as FK) + multivalued attribute value.
    • Composite PK: {FK + Multivalued Attribute}.
    • Example: Employee(emp_id) with dependent_name → Table dependent(emp_id, dname) with PK {emp_id, dname}.
  6. Derived Attributes: NOT stored in tables (computed dynamically).
  7. Generalisation:
    • Method 1: Superclass table + Subclass tables (subclass tables store specific attributes + superclass PK).
    • Method 2: Subclass tables only (stores all inherited attributes). Drawback: Redundant columns if overlapping; fails if incomplete generalisation.

LEC-11: Normalisation & Anomalies 🔥 CodeHelp

1. Functional Dependency (FD)

  • Relationship: $X \rightarrow Y$ ($X$ is Determinant, $Y$ is Dependent).
  • Trivial FD: If $Y \subseteq X$ (e.g. $A \rightarrow A$).
  • Non-trivial FD: If $X \cap Y = \emptyset$.

2. Armstrong’s Axioms

  • Reflexive: If $B \subseteq A$, then $A \rightarrow B$.
  • Augmentation: If $A \rightarrow B$, then $AX \rightarrow BX$.
  • Transitivity: If $A \rightarrow B$ and $B \rightarrow C$, then $A \rightarrow C$.

3. Anomalies (Caused by Data Redundancy)

  1. Insertion Anomaly: Cannot insert valid data without presence of unrelated attributes.
  2. Deletion Anomaly: Deleting one record unintentionally erases other crucial data.
  3. Updation Anomaly: Updating a single value requires modifying multiple rows, risking inconsistency.

4. 1NF (First Normal Form)

Every cell in the table must contain atomic values. No multivalued attributes allowed.

CodeHelp DBMS Master Series Page 22 of 49
LEC-11: 2NF, 3NF & BCNF 🔥 CodeHelp

Normal Forms Hierarchy

  • 2NF (Second Normal Form):
    • Must be in 1NF.
    • No partial dependency: All non-prime attributes must be fully dependent on the entire Primary Key, not a proper part of it.
  • 3NF (Third Normal Form):
    • Must be in 2NF.
    • No transitive dependency: For any $A \rightarrow B$, either $A$ is a Super Key or $B$ is a Prime Attribute. Non-prime attributes must not determine other non-prime attributes.
  • BCNF (Boyce-Codd Normal Form):
    • Must be in 3NF.
    • For every functional dependency $A \rightarrow B$, $A$ must be a Super Key!

Advantages of Normalisation

Minimizes data redundancy, improves database organization, and guarantees data consistency.

LEC-12: Transaction & ACID Properties 🔥 CodeHelp

1. What is a Transaction?

A logical unit of work performed against the database containing one or more SQL statements executed in strict sequence. Must either commit permanently or rollback completely.

2. ACID Properties

  • Atomicity: All operations reflect in DB, or none are (all-or-nothing).
  • Consistency: Preserves integrity constraints before and after execution.
  • Isolation: Concurrent transactions run unaware of each other without interference.
  • Durability: Committed updates persist permanently despite crashes or power cuts.

3. Transaction States

LEC-12: Transaction State Lifecycle Details 🔥 CodeHelp
  1. Active state: Read and write operations are executing.
  2. Partially committed state: Final statement executed; changes buffered in main memory buffer.
  3. Committed state: Changes written permanently to non-volatile disk. Consistent state achieved.
  4. Failed state: Execution aborted due to system/software failure.
  5. Aborted state: Changes reversed via rollback. Prior database state restored.
  6. Terminated state: Life cycle ends after either committing or aborting.

LEC-13: Implementing Atomicity & Durability 🔥 CodeHelp

1. Shadow-Copy Scheme

  • Clones the entire DB into a new copy leaving shadow copy untouched. Updates applied to new copy.
  • Commit: Atomically updates db-pointer sector on disk.
  • Abort: Discards new copy; old copy is safe.
  • Drawback: Highly inefficient copying entire DB per transaction.

2. Log-Based Recovery Schemes (WAL)

  • Deferred DB Modifications: Writes deferred until transaction reaches commit state. Only REDO needed on crash.
  • Immediate DB Modifications: Active transactions write uncommitted changes directly to DB. Crash requires UNDO for uncommitted transactions and REDO for committed ones.

LEC-14: Indexing in DBMS 🔥 CodeHelp

1. Index Fundamentals

Data structure that minimizes disk block I/O accesses when searching records. Search Key points to Data Reference.

2. Index Methods

  • Primary Index (Clustering Index): Data file is sequentially ordered.
    • Sorted on Key: Sparse Index (one entry per data block).
    • Sorted on Non-Key: Dense Index (one entry per unique non-key attribute).
  • Dense vs Sparse Index:
    • Dense: Index record for *every single search key value*.
    • Sparse: Index record appears for only a subset of search key values (e.g. block boundaries).
  • Secondary Index (Non-Clustering): Built on unsorted data files. Always a dense index.
  • Multi-Level Indexing: When primary index exceeds memory, an outer sparse index is layered on top.
CodeHelp DBMS Master Series Page 27 of 49
LEC-14: Tradeoffs of Indexing 🔥 CodeHelp

Advantages:

  1. Faster access and retrieval of data (dramatic reduction in disk I/O).
  2. Enables logarithmic time searches ($O(\log N)$).

Limitations:

  1. Requires additional physical disk space to store index tables.
  2. Decreases performance of INSERT, DELETE, and UPDATE operations because index trees must be balanced on modification.

LEC-15: NoSQL Databases 🔥 CodeHelp

1. What is NoSQL?

"Not Only SQL": Non-tabular databases offering flexible schemas, horizontal scaling, and high availability. Stores data in document, key-value, columnar, or graph structures.

2. Key Advantages

  • Flexible Schema: No need to define rigid tables upfront; schema evolves dynamically.
  • Horizontal Scaling (Scale-Out): Adding commodity hardware nodes across replica-sets or shards without complex distributed joins.
  • High Availability: Automatic replication ensures zero downtime during node failure.
  • High Performance Reads: Data accessed together is stored together, eliminating joins.

LEC-15: Four NoSQL Data Models 🔥 CodeHelp
  1. Key-Value Stores: Simplest model; pairs keys with arbitrary values. Ultra-fast $O(1)$ lookups. Used for session management & caching. Examples: Redis, DynamoDB.
  2. Column-Oriented (Wide-Column): Data organized in columns rather than rows. Exceptional compression and fast analytics. Examples: Cassandra, Snowflake, Redshift.
  3. Document-Based: JSON/BSON documents with embedded nested fields. Ideal for e-commerce catalogs. Supports ACID. Examples: MongoDB, CouchDB.
  4. Graph-Based: Nodes (entities) and Edges (relationships) stored directly. Traverses connections without JOIN overhead. Examples: Neo4j.

LEC-16: Types of Databases 🔥 CodeHelp

Taxonomy of Database Systems

  1. Relational (RDBMS): Discrete normalized tables linked via FKs (MySQL, Oracle).
  2. Object-Oriented (OODBMS): Treats data as objects with OOP inheritance and encapsulation (ObjectDB).
  3. Hierarchical Databases: Tree-like structure where each child has exactly one parent (1:N). Fast for trees, rigid for complex relations (IBM IMS).
  4. Network Databases: Extension of hierarchical model allowing child records to have multiple parent records (M:N) in a graph structure (IDS, IDMS).

LEC-17: Clustering in DBMS 🔥 CodeHelp

1. What is Clustering?

Combining multiple servers/instances to connect to a single database service with synchronized replica sets.

2. Three Primary Advantages

  1. Data Redundancy: Synchronized replicas ensure data survives if any server fails.
  2. Load Balancing: Distributes query workload across nodes, handling massive traffic spikes seamlessly.
  3. High Availability: Service remains online 24/7 even during hardware faults.

LEC-18: Partitioning & Sharding 🔥 CodeHelp

1. Partitioning

Dividing massive database tables into smaller, manageable slices called partitions.

  • Vertical Partitioning: Slicing tables vertically (column-wise).
  • Horizontal Partitioning: Slicing tables horizontally (row-wise).

2. Sharding

Implementing horizontal partitioning across independent physical server nodes with a Routing Layer to direct requests to the correct instance.

  • Pros: Massive horizontal scalability and high availability.
  • Cons: System complexity, re-sharding overhead, and the Scatter-Gather problem for cross-shard analytical queries.

Database Scaling Patterns: Case Study 🔥 CodeHelp

The Problem: Cab Booking Startup

  • Starts with tiny machine handling ~10 customers and 1 booking every 5 minutes.
  • Scales to 30 bookings/minute → Latency spikes, deadlocks, starvation, sluggish app!

  1. Pattern 1: Query Optimisation & Connection Pool (Cache non-dynamic data + reuse DB connections).
  2. Pattern 2: Vertical Scaling (Scale-Up RAM 2x, SSD 3x — cost increases exponentially).
  3. Pattern 3: CQRS (Command Query Responsibility Segregation: 1 Primary for Writes, 2+ Replicas for Reads).
  4. Pattern 4: Multi-Primary Replication (Circular ring where all nodes accept writes).
  5. Pattern 5: Partitioning by Functionality (Separate DBs for Location, Users, and Trips).
  6. Pattern 6: Horizontal Scaling / Sharding (Distribute partitioned shards across 50 nodes).
  7. Pattern 7: Data Centre Wise Partition (Distribute traffic across global continents for low latency & IPO readiness).

LEC-20: CAP Theorem in Distributed Databases 🔥 CodeHelp

1. The CAP Breakdown

  • Consistency (C): All nodes see the exact same data simultaneously. Reads return the most recent write.
  • Availability (A): Every non-failing node returns a response for every request.
  • Partition Tolerance (P): System continues operating despite dropped or delayed messages between nodes.

2. The CAP Theorem Tradeoff

A distributed system can guarantee at most two out of three properties simultaneously:

  • CA Databases: Consistency + Availability (No partition tolerance — impractical in distributed networks; MySQL/Postgres single cluster).
  • CP Databases: Consistency + Partition Tolerance (Turns off inconsistent nodes during partition — crucial for banking; MongoDB).
  • AP Databases: Availability + Partition Tolerance (Nodes remain online and achieve eventual consistency — social networks; Cassandra, DynamoDB).

LEC-21: The Master-Slave Architecture 🔥 CodeHelp

1. Architectural Principle

  • General way to optimize I/O when read query volume surges.
  • Master Database: Handles all Write operations (INSERT, UPDATE, DELETE).
  • Slave Databases: Replicated copies that exclusively handle Read operations (SELECT).

2. DB Replication

  • Replication distributes data from Master to Slaves.
  • Can be synchronous (high consistency, higher latency) or asynchronous (fast writes, potential replication lag).
