Operating System Foundations, Architecture & Process Memory Layout

Source Video: OS Core Concepts Explained | Part 1 • Instructor: Vivek Gupta (Ex-Google, AlgoZenith) • Timeline: 00:00:00 – 00:48:30

Core Takeaway for Technical Interviews

An Operating System is not just a resource allocator; it is a hardware virtualizer and isolation engine. Interviewers at Google, Microsoft, and Amazon routinely evaluate candidate clarity on the precise boundary between User Space and Kernel Space, the hardware mechanics of System Calls, and the exact virtual memory segmentation of an executing binary.

1.1 The Operating System as a Hardware Mediator

At bare metal, a computer system consists of raw electronic hardware: the Central Processing Unit (CPU), Physical Memory (DRAM), and Peripheral I/O Devices (NVMe SSDs, NICs, keyboards). Without an operating system, every user program would need to interface directly with hardware registers, issue raw memory bus commands, and manage physical cylinder sectors on storage media.

The Operating System solves this by functioning as:

  • Resource Allocator: Mediates conflicting hardware requests from multiple concurrently running tasks, ensuring fair access, high utilization, and deadlock prevention.
  • Extended Machine / Abstraction Layer: Hides device-specific low-level complexity (e.g., AHCI/NVMe protocol registers) behind clean, uniform APIs such as standard POSIX file operations (open, read, write, close).
  • Protection and Security Arbiter: Enforces memory boundaries, preventing Rogue Process A from reading or modifying the address space of Process B or corrupting the OS kernel itself.

1.2 Dual-Mode Operation & Hardware Protection

To prevent malicious or buggy applications from halting the CPU or overwriting critical memory structures, modern x86-64 and ARM processors implement hardware-enforced execution privilege levels (Hierarchical Protection Domains, often known as Rings):

  • User Mode (Ring 3): Mode bit set to 1. The CPU restricts access to privileged machine instructions. User applications cannot directly disable interrupts, alter page tables, or perform raw I/O port writes. Attempting to execute a privileged instruction in User Mode immediately triggers a hardware general-protection fault trap.
  • Kernel / Supervisor Mode (Ring 0): Mode bit set to 0. The CPU allows unrestricted execution of all machine instructions, direct hardware port access, and full control over system control registers (such as CR0, CR3 for page table roots on x86).

The System Call Execution Pipeline

When a user-space application requires hardware access (e.g., printing to terminal or reading a disk block), it cannot execute it directly. It must execute a System Call via a software interrupt or specialized machine instruction (⏱️ 48:30):

  1. The user process places system call arguments in designated CPU registers (e.g., on Linux x86-64: RAX holds the system call number, while RDI, RSI, RDX hold parameters).
  2. The process executes the syscall (or legacy int 0x80) instruction.
  3. The CPU hardware saves user program counter (RIP) and stack pointer (RSP), flips the hardware Mode Bit from 1 (User) to 0 (Kernel), and vectors control to the predefined System Call Table in kernel memory.
  4. The kernel inspects RAX, dispatches the corresponding handler function (e.g., sys_read()), verifies user buffer pointers for memory safety, and performs the operation.
  5. Upon completion, the kernel writes the return code into RAX and executes sysret, switching the mode bit back to User Mode (1) and restoring user execution context.

1.3 Program vs. Process: Architectural Distinctions

In placement interviews, candidates often confuse programs with processes (⏱️ 13:01):

Attribute Program Process
Nature Passive entity stored on disk (e.g., compiled ELF binary /usr/bin/ls). Active runtime entity loaded into main memory with allocated CPU cycles.
Lifespan Permanent until deleted from secondary storage. Dynamic; created upon launch, exists through state transitions, destroyed upon termination.
Resource Footprint Consumes only disk storage space. Allocates RAM, CPU registers, stack/heap, file descriptors, and kernel PCB structures.
Relationship One program can spawn multiple distinct processes (e.g., opening 4 separate terminal windows). Each process has its own isolated virtual address space and PID.

1.4 Process Control Block (PCB): The Process Metadata Core

The Operating System represents each process internally using a kernel data structure known as the Process Control Block (PCB) (in the Linux kernel, represented by struct task_struct) (⏱️ 24:28). The PCB contains:

  • Process Identifier (PID): Unique integer identifier assigned by the kernel (e.g., PID 1 is systemd/init).
  • Process State: Current status flag (New, Ready, Running, Waiting, Terminated).
  • Program Counter (PC): Pointer storing the physical/virtual address of the next machine instruction to be executed by the CPU.
  • CPU Registers: Snapshot of all hardware registers (Accumulator, Index, Stack Pointer RSP, Base Pointer RBP, Flags register) saved whenever the process is preempted.
  • Memory Management Information: Base and limit register values, or pointers to the top-level Page Table (e.g., CR3 register value in x86).
  • Accounting & Scheduling Attributes: CPU priority, time slice remaining, CPU time consumed, waiting time accumulated.
  • I/O Status & Open Files: File Descriptor Table (FDT) mapping index integers (0: stdin, 1: stdout, 2: stderr) to kernel file pointers.

1.5 Process Memory Layout (Virtual Address Space Anatomy)

When the OS loads a program into memory, it assigns it a contiguous-looking private virtual address space divided into 4 primary functional segments (⏱️ 33:49):

  1. Text (Code) Segment:
    • Contains the raw compiled executable machine code instructions.
    • Read-Only Protection: Hardware-enforced read-only permission flag to prevent self-modifying code or buffer overflow exploits from altering program logic.
    • Sharable: Multiple concurrent processes executing the same binary (e.g., 10 instances of bash) can safely share the single physical copy of the text segment in RAM.
  2. Data Segment (Initialized Data & BSS):
    • .data: Stores global and static variables explicitly initialized with non-zero values (e.g., int max_users = 500;).
    • .bss (Block Started by Symbol): Stores uninitialized or zero-initialized global and static variables (e.g., static int buffer[1024];). Does not consume binary file space on disk; kernel automatically zero-fills this space upon process instantiation.
  3. Heap Segment:
    • Allocated dynamically at runtime via library calls such as malloc(), calloc(), realloc() in C, or new in C++.
    • Grows upwards toward higher memory addresses. Managed by runtime allocators (e.g., ptmalloc, jemalloc) which invoke kernel system calls brk() or mmap() when expanding.
  4. Stack Segment:
    • Stores activation records (stack frames) for active function calls.
    • Contains function parameters, local automatic variables, caller return addresses, and saved register frames.
    • Grows downwards toward lower memory addresses. Managed automatically by CPU hardware via Stack Pointer (RSP) and Base Pointer (RBP). If stack and heap collide without sufficient address space, a Stack Overflow occurs.

Process Lifecycle, Context Switching & Process Creation Mechanics

Source Video: OS Core Concepts Explained | Part 1 • Instructor: Vivek Gupta (Ex-Google, AlgoZenith) • Timeline: 00:48:30 – 02:06:26

Placement Interview Benchmark

2.1 The Process State Transition Lifecycle

During its execution span, a process transitions between distinct logical states governed by OS kernel events (⏱️ 01:02:15):

stateDiagram-v2 [*] --> New: Program binary initiated New --> Ready: Admitted by Long-Term Scheduler Ready --> Running: Dispatched by Short-Term Scheduler Running --> Ready: Preempted (Timer Interrupt / Time Slice expired) Running --> Waiting: I/O or Event Wait request (Block) Waiting --> Ready: I/O completed or Event Occurred Running --> Terminated: exit() system call or Exception Terminated --> [*]: PCB harvested by parent wait() Ready --> SuspendReady: Memory pressure (Swapped out to Disk) SuspendReady --> Ready: Swapped into RAM Waiting --> SuspendWaiting: Blocked + Low RAM (Swapped to Disk) SuspendWaiting --> SuspendReady: I/O completed while on Disk

State Definitions

  • New: The process is currently being instantiated; memory structures and PCB are being allocated.
  • Ready: The process resides in primary RAM and is queued in the Ready Queue waiting to be assigned CPU execution cycles by the scheduler.
  • Running: The process's machine instructions are actively executing on a physical CPU core.
  • Waiting / Blocked: The process cannot execute even if CPU is idle because it is awaiting an asynchronous external event (e.g., disk I/O, network packet, lock release).
  • Terminated: The process has completed execution via exit(); execution has halted, but its entry remains in the process table until its exit status is collected by its parent.
  • Suspend-Ready & Suspend-Blocked: When physical RAM is exhausted, the Medium-Term Scheduler (Swapper) swaps process address spaces out of RAM into secondary storage (Swap space).

2.2 Context Switching Mechanics & Overhead Analysis

A Context Switch occurs when the CPU scheduler switches the physical processor core from executing Process $P_0$ to executing Process $P_1$ (⏱️ 01:21:40).

The Complete Step-by-Step Context Switch Sequence:

  1. An interrupt (e.g., hardware timer quantum expiration) or a blocking system call traps execution into Kernel Mode.
  2. The CPU dispatcher saves the current execution state of $P_0$ (Program Counter, general-purpose registers, stack pointer, floating-point state) into $P_0$'s PCB in kernel space.
  3. $P_0$'s state in its PCB is updated from Running to Ready (or Waiting).
  4. The scheduler executes its algorithm and selects next process $P_1$ from the Ready Queue.
  5. The kernel updates memory mapping structures (e.g., loading $P_1$'s page table address into CPU control register CR3).
  6. The CPU dispatcher restores all saved registers, stack pointer, and program counter from $P_1$'s PCB into the physical CPU core.
  7. The CPU transitions back to User Mode (Ring 3) and resumes execution of $P_1$ at its saved instruction address.

Direct vs. Indirect Overhead Penalties:

  • Direct Overhead: Time spent executing kernel code to save/restore registers and flush/reload CPU registers (typically 1 to 10 microseconds). Pure computational dead time with zero user-work achieved.
  • Indirect Overhead (Cache Coldness): Loading a new process invalidates the CPU L1/L2 hardware caches and flushes the Translation Lookaside Buffer (TLB). Consequently, the newly resumed process suffers a surge of cache misses and TLB misses until its working set is reloaded into cache, causing significant execution slowdown.

2.3 Process Creation: The fork() & exec() Paradigm

In UNIX/Linux systems, process creation follows a distinct two-step fork-and-exec architecture (⏱️ 01:36:20):

1. The fork() System Call

The fork() system call creates an exact duplicate copy of the calling process:

  • It returns twice from a single invocation:
    • Returns 0 inside the newly created Child Process.
    • Returns the Child's PID ($>0$) inside the Parent Process.
    • Returns a negative integer (-1) if creation fails (e.g., process limit reached).
  • Copy-On-Write (COW) Optimization: Modern operating systems do not duplicate physical RAM pages immediately during fork(). Instead, parent and child share the same physical pages marked as read-only. If either process attempts to write to a page, a hardware page fault triggers the OS to duplicate that specific single page in RAM, giving the writer its own private writable copy. This makes fork() extremely lightweight and instantaneous.

POSIX Implementation Example:

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>

int main() {
    pid_t pid = fork();

    if (pid < 0) {
        // Fork failure
        perror("fork failed");
        exit(EXIT_FAILURE);
    } else if (pid == 0) {
        // Child Process execution path
        printf("[Child Process] PID: %d, Parent PID: %d\n", getpid(), getppid());
        char *args[] = {"/bin/ls", "-l", NULL};
        // Replace child memory with ls program
        execvp(args[0], args);
        // execvp only returns if error occurs
        perror("execvp failed");
        exit(EXIT_FAILURE);
    } else {
        // Parent Process execution path
        printf("[Parent Process] PID: %d, spawned Child PID: %d\n", getpid(), pid);
        int status;
        // Wait for child process to terminate and harvest exit status
        waitpid(pid, &status, 0);
        if (WIFEXITED(status)) {
            printf("[Parent Process] Child terminated with exit code %d\n", WEXITSTATUS(status));
        }
    }
    return 0;
}

2.4 Process Anomalies: Zombie vs. Orphan Processes

Failure to properly coordinate parent and child lifecycles leads to critical system state anomalies (⏱️ 01:52:10):

Feature Zombie Process (Defunct) Orphan Process
Definition A process that has finished execution (invoked exit()), but whose parent has not yet called wait() / waitpid(). A process that is still running, but whose parent process has terminated prematurely.
Resource Usage Releases all RAM memory (text, data, heap, stack) and closed file descriptors; retains only its PCB entry and PID slot in the process table. Continues actively consuming CPU cycles, RAM, and I/O resources as a normal process.
System Hazard Accumulating thousands of zombie processes causes PID Exhaustion, preventing any new process from spawning in the system. Minor; could waste background CPU if forgotten, but safe.
Resolution / Cleanup The parent must call wait(). If the parent is stuck in a loop, terminating the parent forces adoption by PID 1, which cleans up the zombie. Automatically adopted by system root process (PID 1: systemd or init), which periodically issues wait() to harvest child status upon exit.

CPU Scheduling Fundamentals & Classic Scheduling Algorithms

Source Video: OS Scheduling & Multicore Systems | Part 2 • Instructor: Vivek Gupta (Ex-Google, AlgoZenith) • Timeline: 00:00:00 – 00:36:29

Mathematical Rigor in Placement Interviews

CPU scheduling interview problems are intensely quantitative. You will be given a table of 4 to 5 processes with arrival times, burst times, and priorities, and asked to compute exact Completion Time, Turnaround Time, and Waiting Time across FCFS, SJF, SRTF, and Round Robin using clear Gantt Charts.

3.1 Scheduling Objectives & Criteria Metrics

The CPU scheduler is the heart of multiprogramming. Since real-world processes alternate between CPU Bursts (executing code) and I/O Bursts (waiting for network, disk, or user input), scheduling maximizes CPU utilization by giving the CPU to another ready process whenever the current process enters an I/O wait state (⏱️ 04:44).

The 5 Golden Scheduling Performance Metrics:

  1. CPU Utilization: The percentage of total time the CPU is actively performing user or system computation (Goal: Maximize, practically 40% to 90%).
  2. Throughput: The number of complete processes executed per unit time (Goal: Maximize).
  3. Turnaround Time (TAT): The total elapsed time from the moment a process is submitted until its complete termination: $$\text{TAT} = \text{Completion Time (CT)} - \text{Arrival Time (AT)}$$ (Goal: Minimize).
  4. Waiting Time (WT): The cumulative time a process spends waiting in the Ready Queue: $$\text{WT} = \text{Turnaround Time (TAT)} - \text{Burst Time (BT)}$$ (Goal: Minimize).
  5. Response Time (RT): The time elapsed between process arrival and its very first execution on the CPU: $$\text{RT} = \text{Time of First CPU Dispatch} - \text{Arrival Time (AT)}$$ (Goal: Minimize; crucial for interactive UX).

3.2 Scheduler Taxonomy & Dispatcher Role

An operating system utilizes three distinct types of schedulers acting at different operational timescales (⏱️ 07:33):

  • Long-Term Scheduler (Job Scheduler): Selects processes from secondary storage (pool of batch jobs) and loads them into primary RAM ready queue. Regulates the Degree of Multiprogramming (total processes in memory). Invoked infrequently (seconds to minutes).
  • Short-Term Scheduler (CPU Scheduler): Selects which in-memory ready process is allocated the physical CPU. Invoked very frequently (every 10 to 100 milliseconds), hence must be exceptionally fast.
  • Medium-Term Scheduler (Swapper): Handles swapping out processes from RAM to Swap disk during severe memory pressure, and swapping them back when RAM frees up.
  • Dispatcher: The low-level kernel module that physically performs the context switch, switches the CPU to user mode, and jumps to the proper location in the user program. The elapsed time taken by the dispatcher to halt one process and start another is called Dispatch Latency.

3.3 Preemptive vs. Non-Preemptive Scheduling

  • Non-Preemptive Scheduling: Once a process is allocated the CPU, it holds the CPU until it voluntarily yields control—either by terminating (exit()) or by requesting I/O (transition to Waiting state). No timer interrupts can forcibly take the CPU away.
    Pros: Simple, low overhead, deterministic.
    Cons: Poor interactive response, vulnerable to rogue infinite loops.
  • Preemptive Scheduling: The OS kernel can forcibly interrupt and confiscate the CPU from an actively running process (e.g., when a higher-priority job arrives or the hardware timer interrupt signals time slice expiration).
    Pros: Excellent responsiveness, prevents starvation in interactive environments.
    Cons: Incurs higher context switch overhead; requires synchronization locks on shared kernel data structures to prevent race conditions.

3.4 First-Come, First-Served (FCFS) Scheduling

The simplest scheduling algorithm. Implemented via a standard FIFO queue (⏱️ 14:26). Non-preemptive.

The Convoy Effect Hazard:

If a massive CPU-bound process arrives first, all short, interactive I/O-bound processes are trapped behind it in the ready queue. While the giant process runs on CPU, the I/O devices sit idle. When the giant process finally blocks for I/O, all short processes quickly blast through CPU and block for I/O, leaving the CPU idle. This severe degradation in device and CPU utilization is called the Convoy Effect.

3.5 Shortest Job First (SJF) & Shortest Remaining Time First (SRTF)

Assigns the CPU to the process with the smallest subsequent CPU burst length (⏱️ 15:28).

  • Non-Preemptive SJF: Once granted, the process runs to completion of its burst. Provably achieves the minimal average waiting time among all non-preemptive algorithms.
  • Preemptive SJF (SRTF): If a new process arrives with a remaining CPU burst shorter than the remaining burst of the currently running process, the current process is immediately preempted.

Burst Time Estimation via Exponential Smoothing:

Because the OS cannot know future CPU bursts in advance, it predicts the next burst $\tau_{n+1}$ using past historical burst $t_n$ via exponential averaging:

$$\tau_{n+1} = \alpha t_n + (1 - \alpha) \tau_n \quad \text{where } 0 \le \alpha \le 1$$

Typically $\alpha = 0.5$, balancing recent behavior with long-term historical baseline.

3.7 Round Robin (RR) Scheduling

Designed specifically for time-sharing interactive systems (⏱️ 30:47). Each process is allocated a small unit of CPU time called a Time Quantum ($q$) or time slice (typically 10 to 100 ms). Processes are held in a circular FIFO queue.

The Time Quantum Dilemma:

  • If $q \to \infty$: Round Robin degenerates into FCFS, suffering from the Convoy Effect.
  • If $q \to 0$: Round Robin approaches Processor Sharing, where $n$ processes run at $1/n$ speed, but the system spends nearly 100% of CPU time executing context switches, collapsing throughput.
  • Rule of Thumb: Approximately 80% of CPU bursts should be shorter than the time quantum $q$ to minimize context switches while preserving rapid interactive response.

3.8 Priority Scheduling & The Aging Mitigation

Each process is assigned a priority integer $p$. The CPU is allocated to the highest-priority process (⏱️ 34:28).

  • Starvation (Indefinite Blocking): A low-priority process may sit in the ready queue indefinitely if a steady stream of higher-priority processes keeps arriving. (Legendary real-world case: When the IBM 7094 at MIT was shut down in 1973, a low-priority job submitted in 1967 was discovered still waiting!).
  • Aging Solution: A technique of gradually incrementing the priority of processes that wait in the system for long durations. Eventually, any aged process achieves the highest priority and is guaranteed CPU dispatch.

Multilevel Queues, Multicore Systems & Multiprocessor Scheduling

Source Video: OS Scheduling & Multicore Systems | Part 2 • Instructor: Vivek Gupta (Ex-Google, AlgoZenith) • Timeline: 00:36:29 – 00:55:33

Placement Relevance: System Architecture & Modern Concurrency

Top tech companies expect candidates to comprehend how CPU scheduling scales beyond single-core setups to modern multi-socket, multicore machines. Key questions involve Multilevel Feedback Queue (MLFQ) parameter design, CPU Cache Affinity (Soft vs Hard), NUMA architectural bottlenecks, and Load Balancing mechanics (Push vs Pull migration).

4.1 Multilevel Queue (MLQ) Scheduling

In real-world operating systems, processes differ drastically in their behavioral demands. Interactive foreground UI tasks require rapid response times, while background batch computational tasks require maximum throughput without user interruption (⏱️ 36:29).

Multilevel Queue Scheduling partitions the single Ready Queue into multiple distinct prioritized queues:

graph TD P[Incoming Processes] --> Q1["Queue 1: System Processes (Highest Priority - FCFS/Priority)"] P --> Q2["Queue 2: Interactive UI Processes (Medium-High - Round Robin q=8ms)"] P --> Q3["Queue 3: Interactive Editing Processes (Medium - Round Robin q=16ms)"] P --> Q4["Queue 4: Batch Processing Jobs (Lowest Priority - FCFS)"] Q1 --> CPU[Physical CPU Core] Q2 -.->|Only runs if Q1 empty| CPU Q3 -.->|Only runs if Q1, Q2 empty| CPU Q4 -.->|Only runs if Q1, Q2, Q3 empty| CPU
  • Processes are permanently assigned to one queue based on their inherent characteristics (e.g., memory size, process priority, or type).
  • Each queue executes its own independent scheduling algorithm (e.g., Round Robin for foreground, FCFS for background).
  • Inter-Queue Scheduling: Typically implemented as strict fixed-priority preemptive scheduling (e.g., Queue 1 preempts Queue 2). If foreground queues are constantly saturated, background batch queues suffer severe Starvation.

4.2 Multilevel Feedback Queue (MLFQ) Scheduling

To eliminate process starvation and avoid requiring upfront knowledge of process CPU burst lengths, modern OS kernels implement the Multilevel Feedback Queue (MLFQ). MLFQ allows processes to dynamically migrate between queues based on their observed runtime behavior.

The 5 Fundamental Rules of MLFQ:

  1. Rule 1: If $\text{Priority}(A) > \text{Priority}(B)$, process $A$ runs and process $B$ does not.
  2. Rule 2: If $\text{Priority}(A) = \text{Priority}(B)$, processes $A$ and $B$ run in Round Robin using the time quantum of that queue.
  3. Rule 3: When a new job enters the system, it is placed at the highest priority queue (assuming it is short/interactive).
  4. Rule 4 (Demotion): Once a process uses up its allocated time allotment at a given priority level (regardless of how many times it yielded the CPU for I/O), its priority is demoted down by one level. (Prevents gaming the scheduler with tiny I/O bursts).
  5. Rule 5 (Priority Boost): After some fixed global time period $S$, all processes in the system are moved to the topmost priority queue. (Solves Starvation for CPU-bound batch jobs and adapts if a batch job transitions into an interactive phase).

4.3 Multiprocessor & Multicore Architecture Overview

Modern computers feature multiple CPUs, multicore dies, and hyper-threaded execution pipelines (⏱️ 40:48):

  • Asymmetric Multiprocessing (AMP): One master CPU core handles all OS kernel data structures, scheduling, and I/O processing, while worker cores execute only user code. Eliminates data sharing bottlenecks but creates a master CPU bottleneck.
  • Symmetric Multiprocessing (SMP): Each processor core is self-scheduling. All cores access common ready queues or run private per-core run-queues. Standard architecture in modern Linux, Windows, and macOS.
  • Hardware Multithreading (Hyper-Threading / SMT): A single physical core provides multiple architectural hardware threads (e.g., 2 virtual cores per physical core). Hardware threads share execution units (ALU, FPU) and caches, interleaving instruction streams whenever one thread stalls on a memory fetch latency.

4.4 Processor Affinity: Soft vs. Hard Affinity

When a process executes on CPU Core 0, its memory footprint (data, variables, stack) is heavily populated into Core 0's private L1 and L2 caches. If the scheduler moves this process to Core 1 on the next time slice, Core 0's cache becomes useless, and the process experiences heavy memory bus latency reloading its cache lines on Core 1.

  • Processor Affinity: The OS scheduler attempts to keep a process running on the exact same physical core to exploit warm hardware cache lines.
  • Soft Affinity: The kernel has a strong policy preference to keep a process on its current core, but permits migration if workload imbalance demands it.
  • Hard Affinity: The system guarantees that a process will execute strictly on a user-specified subset of cores (e.g., using Linux sched_setaffinity() system call). Frequently configured in high-frequency trading (HFT) and real-time telecom engines.

4.5 Non-Uniform Memory Access (NUMA) Architecture

In multi-socket enterprise servers, memory access latency is non-uniform. Each CPU socket has its own directly attached local RAM bank, connected to other CPU sockets via high-speed interconnects (e.g., Intel UPI, AMD Infinity Fabric):

NUMA-Aware Scheduling: The scheduler must allocate memory from the local memory node of the CPU currently executing the thread, and strictly avoid migrating threads across sockets to prevent severe memory bus bottlenecks.

4.6 Load Balancing: Push vs. Pull Migration

To maximize parallelism on SMP systems with private per-core run-queues, the kernel must continuously balance workload across cores:

  • Push Migration: A dedicated kernel daemon (e.g., ksoftirqd in Linux) periodically monitors the load on all processor cores. If an imbalance exceeds a threshold, it forcibly pushes processes from an overloaded queue into an underloaded or idle core's queue.
  • Pull Migration: An idle processor core that finishes all tasks in its private queue actively reaches into the queue of a busy core and pulls a waiting process into its own queue.
  • Trade-off with Processor Affinity: Aggressive load balancing destroys cache affinity, whereas strict affinity causes load imbalance. Modern schedulers (like Linux Completely Fair Scheduler / CFS) balance these with hierarchical scheduling domains.

5.2 Address Binding: Compile-Time, Load-Time & Execution-Time

Before a program can execute, its instructions and variables must be bound to physical memory addresses (⏱️ 14:36):

  • Compile-Time Binding: If it is known at compile time where the process will reside in memory, absolute physical code is generated (e.g., MS-DOS .COM files). If starting location changes, the entire code must be recompiled.
  • Load-Time Binding: Compiler generates relocatable code. Final physical binding is delayed until the loader places the program into memory. If the process is swapped out and reloaded at a different physical base, addresses are invalid.
  • Execution-Time (Run-Time) Binding: Binding is delayed until the exact instant the instruction is executed by the CPU. Requires hardware support: the Memory Management Unit (MMU) with dynamic relocation base and limit registers. This is the universal standard in all modern multi-tasking operating systems.

5.3 Contiguous Memory Allocation & Fragmentation

In early multiprogramming systems, each process was loaded into a single contiguous block of physical RAM (⏱️ 17:25):

1. Fixed Partitioning (Multiprogramming with Fixed Tasks - MFT):

  • RAM is divided into fixed-sized partitions at boot time.
  • Internal Fragmentation: Occurs when the memory allocated to a process is slightly larger than the memory requested by the process. The unused space within the allocated partition is wasted and cannot be used by other processes.

2. Variable Partitioning (Multiprogramming with Variable Tasks - MVT):

  • Partitions are created dynamically to match the exact size requested by incoming processes.
  • External Fragmentation: As processes terminate and leave holes in RAM, the total free memory across the system is sufficient to satisfy an incoming request, but it is broken up into small, non-contiguous fragments.
  • Compaction: Moving all allocated blocks to one end of memory to coalesce scattered holes into one large block. Heavy CPU and bus overhead; only possible if run-time dynamic relocation is supported.

Dynamic Storage Allocation Strategies:

  • First-Fit: Allocate the first available hole that is large enough. Search stops immediately upon finding a valid hole. (Fastest, very efficient in practice).
  • Best-Fit: Allocate the smallest hole that is large enough. Requires searching the entire free list (unless sorted). Leaves behind tiny, unusable leftover holes.
  • Worst-Fit: Allocate the largest available hole. Requires searching entire list. Leaves behind largest leftover hole, which may be useful for subsequent allocations. (Performs worst in practice).

5.4 Segmentation: Programmer-Centric Logical Architecture

A user program does not view memory as a linear array of bytes; rather, it views memory as a collection of variable-length logical segments: the main function, helper routines, stack, heap, and symbol tables (⏱️ 21:32).

Hardware Address Translation in Segmentation:

A logical address is a tuple $\langle s, d \rangle$, where $s$ is the Segment Number and $d$ is the Segment Offset:

5.5 Paging: The Universal Non-Contiguous Solution

Paging breaks physical memory and logical address space into fixed-sized chunks, eliminating external fragmentation completely (⏱️ 26:15):

  • Frames: Physical memory is divided into fixed-sized blocks called Frames (typically 4 KB).
  • Pages: Logical address space is divided into blocks of the exact same size called Pages.
  • Any free physical frame can be assigned to any page of any process.

Mathematical Address Translation in Paging:

Let the virtual address space be $2^n$ bytes and page size be $2^m$ bytes:

  • The higher $n - m$ bits represent the Page Number ($p$).
  • The lower $m$ bits represent the Page Offset ($d$) within the page.

Solved Concrete Interview Example:

Problem: Consider a 32-bit system with a 4 KB page size. What is the breakdown of the logical address, and how large is a linear Page Table assuming each Page Table Entry (PTE) is 4 bytes?

  • Page size $= 4 \text{ KB} = 2^{12} \text{ bytes} \implies m = 12 \text{ bits}$ for Page Offset ($d$).
  • Virtual address space $= 32 \text{ bits} \implies n = 32 \text{ bits}$.
  • Page Number bits $= n - m = 32 - 12 = 20 \text{ bits}$.

  • Page Table Size $= 2^{20} \text{ entries} \times 4 \text{ bytes/entry} = 4 \text{ MB per process!}$

Internal Fragmentation in Paging: Paging completely eliminates External Fragmentation. However, it incurs slight Internal Fragmentation on the very last page of a process (on average, half a page $\approx 2 \text{ KB}$).

6.1 Translation Lookaside Buffer (TLB) & EMAT Calculations

In basic paging, every memory reference requires two physical RAM accesses: first to read the Page Table Entry (PTE) from RAM, and second to read/write the actual operand. This doubles memory latency and halves processor throughput (⏱️ 33:37).

The Translation Lookaside Buffer (TLB) is an associative hardware cache embedded directly inside the Memory Management Unit (MMU) that stores recent $\langle \text{Page Number}, \text{Frame Number} \rangle$ translations.

The Complete EMAT Formula:

Let $h$ be the TLB Hit Ratio ($0 \le h \le 1$), $t_{\text{tlb}}$ be the TLB search time, and $t_{\text{mem}}$ be the physical RAM access time:

$$\text{EMAT} = h \cdot (t_{\text{tlb}} + t_{\text{mem}}) + (1 - h) \cdot (t_{\text{tlb}} + 2 \cdot t_{\text{mem}})$$

Solved Placement Numerical:

Given: TLB access time $t_{\text{tlb}} = 10 \text{ ns}$, RAM access time $t_{\text{mem}} = 100 \text{ ns}$, TLB Hit Ratio $h = 95\% = 0.95$.

$$\text{On TLB Hit:} \quad 10 + 100 = 110 \text{ ns}$$

$$\text{On TLB Miss:} \quad 10 + 100 (\text{page table}) + 100 (\text{data}) = 210 \text{ ns}$$

$$\text{EMAT} = 0.95 \times 110 + 0.05 \times 210 = 104.5 + 10.5 = 115 \text{ ns}$$

Notice that with a 95% hit ratio, effective access slows from 100 ns to only 115 ns (a mere 15% slowdown instead of a 100% doubling!).

6.2 Virtual Memory & Demand Paging Mechanics

Virtual Memory decouples the logical address space perceived by user programs from physical RAM capacity (⏱️ 37:27). An application can allocate a 64 GB address space on a machine with only 8 GB of physical RAM.

Demand Paging & The Valid-Invalid Bit:

Under Demand Paging, pages are not preloaded into RAM at startup. Pages are loaded lazily only when the executing CPU actively references an instruction or data byte residing on that page.

  • Each entry in the Page Table includes a Valid-Invalid Bit ($v/i$):
    • Valid (v): The page is legally present in physical RAM. Translation proceeds immediately at hardware speed.
    • Invalid (i): The page is either outside the legal address space of the process, or is a valid page currently residing on secondary swap storage. Access triggers a Page Fault.

6.3 The 7-Step Page Fault Handling Routine

When the CPU attempts to access an address marked with an invalid bit, the MMU cannot complete the translation and raises a hardware trap to the OS kernel (⏱️ 39:50):

Page Fault Overhead Impact:

Disk I/O latency is approximately $8 \text{ ms} = 8,000,000 \text{ ns}$, whereas RAM access is $100 \text{ ns}$. If the page fault rate is denoted $p$, the effective access time is:

$$\text{EAT} = (1 - p) \cdot 100 \text{ ns} + p \cdot 8,000,000 \text{ ns}$$

Even if only 1 out of 100,000 accesses ($p = 0.00001$) triggers a page fault, memory access speed slows down by almost a factor of two! Hence, optimal page replacement algorithms are critical.

6.4 Page Replacement Algorithms

When a page fault occurs and all physical frames in RAM are occupied, the OS must select a victim frame to page out to disk (⏱️ 48:20):

1. First-In, First-Out (FIFO) & Belady's Anomaly:

The oldest loaded page in memory is chosen as victim.

Belady's Anomaly Defined

Normally, providing more physical RAM frames reduces the number of page faults. In FIFO Page Replacement, however, increasing the number of allocated physical frames can paradoxically increase the total number of page faults for certain reference strings! (e.g., Reference string: 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 yields 9 faults with 3 frames, but 10 faults with 4 frames!). Stack-based algorithms (OPT, LRU) are provably immune to Belady's Anomaly.

2. Optimal Page Replacement (OPT / MIN):

Replace the page that will not be referenced for the longest duration of time in the future. Provably guarantees the lowest possible page fault rate for any fixed number of frames. However, it is unimplementable in general-purpose systems because the OS cannot foresee the future. It serves as an optimal theoretical upper bound benchmark for evaluating practical algorithms.

3. Least Recently Used (LRU) Algorithm:

Approximates the Optimal algorithm by using the recent past as an approximation of the near future: replace the page that has not been referenced for the longest period of time (⏱️ 52:05).

  • Counter / Timestamp Implementation: Every page table entry contains a time-of-use field. On every memory access, copy CPU clock into the PTE. On replacement, scan all entries for smallest time value. High overhead ($O(N)$ scan).
  • Doubly-Linked List Stack: Maintain a stack of page numbers. Whenever a page is accessed, unlink it and move it to the top of the stack. The bottom of the stack is always the LRU victim frame ($O(1)$ replacement, but memory pointer updates on every access).

4. Clock / Second-Chance Algorithm:

Hardware approximation of LRU. Uses a circular queue and a single Reference Bit per frame:

  • When a page is accessed, hardware sets Reference Bit $= 1$.
  • When replacement is needed, the pointer moves circularly through the frames:
    • If Reference Bit $== 1$: Clear bit to $0$ and advance pointer (gives page a second chance).
    • If Reference Bit $== 0$: Select this frame as victim immediately!

6.5 Thrashing & The Working Set Model

If a process does not have enough physical frames allocated to hold its currently active working pages, it faults rapidly. The CPU scheduler sees processes blocking on I/O, assumes the CPU is underutilized, and increases the Degree of Multiprogramming by admitting more processes into RAM. This further starves existing processes of frames, plunging the system into Thrashing: a pathological state where the computer spends nearly 100% of its time swapping pages in and out of disk, while productive CPU utilization collapses to near zero (⏱️ 58:20).

Solution: The Working Set Model ($W(t, \Delta)$):

Peter Denning's Working Set Model defines the working set of a process as the set of distinct pages referenced in the most recent $\Delta$ page references (the Working Set Window). The OS calculates total demand $D = \sum |W_i|$. If $D > \text{Total Physical Frames}$, the OS immediately suspends/swaps out an entire process to free up frames, guaranteeing thrashing never occurs.

7.2 Introduction to Deadlocks

A Deadlock is a situation where a set of concurrent processes are permanently blocked because each process holds a resource and waits for another resource held by another process in the same set (⏱️ 15:42).

graph LR P1((Process P1)) -->|Request Edge: Waiting for R2| R2[Resource R2] R2 -->|Assignment Edge: Held by P2| P2((Process P2)) P2 -->|Request Edge: Waiting for R1| R1[Resource R1] R1 -->|Assignment Edge: Held by P1| P1

Deadlock vs. Starvation vs. Livelock:

  • Deadlock: Two or more processes are trapped in a circular waiting state. No process can make progress, and no CPU cycles are consumed.
  • Starvation (Indefinite Blocking): A process waits indefinitely because other higher-priority processes continually preempt the resources. The system as a whole makes progress, but the victim process does not.
  • Livelock: Two or more processes actively change their states in response to each other, but without doing any useful work (e.g., two polite people in a narrow hallway continually stepping to the same side simultaneously). Consumes 100% CPU.

7.3 Coffman's 4 Necessary Conditions for Deadlock

Edward G. Coffman Jr. proved in 1971 that a deadlock can arise if and only if all four of the following conditions hold simultaneously (⏱️ 20:07):

  1. Mutual Exclusion: At least one resource must be non-shareable (only one process can use the resource at any given instant).
  2. Hold and Wait: A process must be currently holding at least one resource and simultaneously requesting additional resources held by other processes.
  3. No Preemption: Resources cannot be forcibly seized from a process; they can only be released voluntarily by the process holding them after task completion.
  4. Circular Wait: A closed chain of processes $\{P_0, P_1, \dots, P_n\}$ exists such that $P_0$ is waiting for a resource held by $P_1$, $P_1$ is waiting for a resource held by $P_2$, $\dots$, and $P_n$ is waiting for a resource held by $P_0$.

7.4 Resource Allocation Graph (RAG) Architecture

The OS tracks resource allocations using a directed bipartite graph $G = (V, E)$ (⏱️ 23:14):

  • Vertices $V$: Process nodes $P = \{P_1, \dots, P_n\}$ (drawn as circles) and Resource nodes $R = \{R_1, \dots, R_m\}$ (drawn as rectangles containing dots representing individual resource instances).
  • Edges $E$:
    • Request Edge ($P_i \to R_j$): Directed from process circle to resource rectangle; indicates process $P_i$ has requested an instance of $R_j$ and is currently waiting.
    • Assignment Edge ($R_j \to P_i$): Directed from a specific instance dot inside $R_j$ to process circle $P_i$; indicates the instance has been granted to $P_i$.

The Cycle Theorem in Deadlock Detection:

Single-Instance vs. Multi-Instance Cycle Theorem

  • If each resource type has exactly 1 instance: A cycle in the Resource Allocation Graph is a necessary AND sufficient condition for deadlock. Cycle $\iff$ Deadlock!
  • If resource types have multiple instances: A cycle is a necessary but NOT sufficient condition for deadlock. A cycle may exist without deadlock if processes outside the cycle eventually release other instances of the contentious resources, breaking the dependency.

7.5 Deadlock Handling Strategies & Prevention

  1. Deadlock Ignorance (The Ostrich Algorithm): Stick your head in the sand and pretend deadlocks never happen (⏱️ 29:09). Because deadlocks occur rarely in well-written software and formal avoidance algorithms carry heavy runtime overhead, this is the standard strategy chosen by modern general-purpose operating systems like Linux and Windows. If a deadlock occurs, reboot or kill the offending process manually.
  2. Deadlock Prevention: Formally guarantee that at least one of Coffman's 4 conditions can never hold:
    • Eliminate Mutual Exclusion: Make resources sharable (e.g., read-only files, print spoolers). Impossible for intrinsically non-shareable hardware like mutexes or tape drives.
    • Eliminate Hold and Wait: Protocol 1: Require processes to request all needed resources at once at startup. Protocol 2: Process must release all currently held resources before requesting any new ones. (Causes low resource utilization and starvation).
    • Eliminate No Preemption: If a process holding resources requests an unavailable resource, the OS forcibly preempts all currently held resources and puts them into a waiting pool until all can be acquired together.
    • Eliminate Circular Wait: Impose a global strict total ordering on all resources: $F: R \to \mathbb{N}$. A process can only request resource $R_j$ if $F(R_j) > F(R_i)$ for all currently held resources $R_i$. This is the most practical and widely implemented prevention strategy.

7.6 Deadlock Avoidance: Banker's Algorithm Solved Numerical

Rather than statically restricting resource requests, Deadlock Avoidance dynamically inspects every resource allocation request to verify that granting it keeps the system in a Safe State (⏱️ 33:08).

A state is defined as Safe if there exists at least one safe execution sequence $\langle P_0, P_1, \dots, P_{n-1} \rangle$ where each process can finish using currently available resources plus resources released by all predecessor processes.

The Banker's Algorithm Data Structures:

  • $\text{Available}[m]$: Vector of length $m$ (available instances of each resource type).
  • $\text{Max}[n][m]$: Maximum demand of process $P_i$ for resource $R_j$.
  • $\text{Allocation}[n][m]$: Currently allocated instances to process $P_i$.
  • $\text{Need}[n][m] = \text{Max}[i][j] - \text{Allocation}[i][j]$: Remaining instances process $P_i$ may request.

  7. Check P4: $\text{Need}_4 = [4, 3, 1] \le [10, 5, 5]$? True!
    $\text{Work} = [10, 5, 5] + [0, 0, 2] = [10, 5, 7]$. Set $\text{Finish}[4] = \text{true}$.

8.1 Race Conditions & The Critical Section Problem

When multiple cooperating processes or threads concurrently read and write shared memory or global variables, the final output depends unpredictably on the exact sequence and timing of instruction execution. This non-deterministic timing bug is called a Race Condition (⏱️ 00:00).

The 4 Code Sections of Cooperating Processes:

  1. Entry Section: Requests permission to access the shared resource.
  2. Critical Section: The code region where shared memory, files, or tables are actively manipulated.
  3. Exit Section: Signals completion and releases access permissions.
  4. Remainder Section: Non-shared, private computational execution.

The 3 Mandatory Criteria for Any Valid Critical Section Solution:

  1. Mutual Exclusion: If process $P_i$ is executing in its critical section, no other process can be executing in their critical sections simultaneously.
  2. Progress: If no process is in its critical section and some processes wish to enter, only those processes not executing in their remainder sections can participate in deciding who enters next, and this selection cannot be postponed indefinitely (no deadlock).
  3. Bounded Waiting: There must exist a bound (limit) on the number of times other processes are allowed to enter their critical sections after a process has made a request to enter and before that request is granted (no starvation).

8.2 Software Solutions: Peterson's Algorithm

Gary Peterson proposed an elegant pure software solution for 2 processes ($P_0$ and $P_1$) in 1981 (⏱️ 03:28):

Shared State Variables:

int turn;          // Indicates whose turn it is to enter
bool flag[2];      // flag[i] == true indicates Pi is ready to enter

Process $P_i$ Implementation (where $j = 1 - i$):

while (true) {
    flag[i] = true;      // Declare intention to enter
    turn = j;            // Be polite: grant priority to competitor
    
    // Busy wait while competitor is interested AND it is their turn
    while (flag[j] && turn == j);
    
    // CRITICAL SECTION
    // Access shared memory variables safely
    
    flag[i] = false;     // EXIT SECTION: revoke intention
    
    // REMAINDER SECTION
}

Proof of Correctness:

  • Mutual Exclusion: For both $P_0$ and $P_1$ to enter the critical section simultaneously, both flag[0] == true and flag[1] == true. However, the value of variable turn can only be either $0$ or $1$ at any given moment, never both. If turn == 0, $P_1$ is trapped in its while loop. Thus, Mutual Exclusion is guaranteed.
  • Progress: A process cannot enter unless the other process sets flag[j] = true and turn = i. If $P_j$ is in remainder section, flag[j] == false, allowing $P_i$ to enter instantly without delay.
  • Bounded Waiting: Once $P_j$ exits, it sets flag[j] = false. If it immediately loops and tries to re-enter, it sets turn = i, forcing itself to wait and granting $P_i$ access. $P_i$ waits at most 1 turn.

Limitation on Modern CPUs: Out-of-order execution, instruction pipelines, and compiler memory reordering can swap the statements flag[i] = true and turn = j on modern multicore hardware, breaking software-only synchronization unless explicit Memory Barriers are inserted.

8.4 Mutex Locks vs. Spinlocks

  • Mutex Lock (Mutual Exclusion): A boolean lock variable provided by the kernel (e.g., pthread_mutex_t). If the lock is held, the calling thread is put to sleep by the kernel and yields CPU to other processes.
  • Spinlock: A mutex lock where waiting threads loop continuously (busy-wait) on the CPU checking the lock condition (⏱️ 16:41).
    Engineering Trade-off: Spinlocks waste CPU cycles on single-core systems. On multi-core systems, however, if the critical section is extremely brief (shorter than the context switch latency of 5 μs), a spinlock is substantially faster than putting a thread to sleep and waking it back up!

8.5 Semaphores: Binary vs. Counting

Invented by Edsger Dijkstra, a Semaphore $S$ is an integer variable accessed exclusively through two standard atomic operations: wait() (or $P$ from Dutch proberen to test) and signal() (or $V$ from verhogen to increment) (⏱️ 19:47):

  • Binary Semaphore: Integer value restricted between $0$ and $1$. Functions identically to a Mutex lock.
  • Counting Semaphore: Value initialized to integer $N$, controlling access to a finite pool of $N$ identical resource instances.

8.6 Classic Concurrency Problems with C POSIX Implementations

1. The Bounded-Buffer (Producer-Consumer) Problem (⏱️ 27:36)

Producers insert items into a fixed-capacity buffer of size $N$; Consumers remove items. Semaphores required:

  • sem_t mutex; initialized to 1 (mutual exclusion on buffer access).
  • sem_t empty; initialized to N (tracks available empty slots).
  • sem_t full; initialized to 0 (tracks available filled items).
// Producer Thread
void *producer(void *arg) {
    while (1) {
        item_t item = produce_item();
        sem_wait(&empty);    // Decrement empty slots (blocks if buffer full)
        sem_wait(&mutex);    // Acquire buffer lock
        
        insert_into_buffer(item);
        
        sem_post(&mutex);    // Release buffer lock
        sem_post(&full);     // Increment full slots (wakes consumer)
    }
}

// Consumer Thread
void *consumer(void *arg) {
    while (1) {
        sem_wait(&full);     // Decrement full slots (blocks if buffer empty)
        sem_wait(&mutex);    // Acquire buffer lock
        
        item_t item = remove_from_buffer();
        
        sem_post(&mutex);    // Release buffer lock
        sem_post(&empty);    // Increment empty slots (wakes producer)
        consume_item(item);
    }
}

Deadlock Trap in Placement Interviews

If the producer executes sem_wait(&mutex) before sem_wait(&empty) when the buffer is completely full, it locks the buffer and blocks waiting for empty space. The consumer tries to run, but blocks on mutex, producing an immediate, permanent Deadlock!

2. The Readers-Writers Problem (⏱️ 32:41)

Multiple concurrent readers can read simultaneously, but writers must have exclusive access.

  • sem_t rw_mutex; initialized to 1 (locks the shared database).
  • sem_t mutex; initialized to 1 (protects reader counter).
  • int read_count = 0;
// Reader Routine
void *reader(void *arg) {
    sem_wait(&mutex);
    read_count++;
    if (read_count == 1) {
        sem_wait(&rw_mutex); // First reader locks out all writers
    }
    sem_post(&mutex);

    // Reading dataset concurrently

    sem_wait(&mutex);
    read_count--;
    if (read_count == 0) {
        sem_post(&rw_mutex); // Last reader releases lock for writers
    }
    sem_post(&mutex);
}

// Writer Routine
void *writer(void *arg) {
    sem_wait(&rw_mutex);     // Exclusive access
    // Writing/modifying dataset
    sem_post(&rw_mutex);
}

5 philosophers sit around a table with 5 bowls of rice and 5 chopsticks. A philosopher needs both adjacent chopsticks to eat.

  • Deadlock Hazard: If all 5 philosophers simultaneously pick up their left chopstick, all right chopsticks are occupied, creating a circular wait cycle.
  • Standard Solutions:
    1. Allow at most 4 philosophers to sit at the table simultaneously.
    2. Asymmetric Solution: Odd-numbered philosophers pick up left chopstick first, then right; even-numbered philosophers pick up right chopstick first, then left. Breaks Circular Wait condition!

9.1 Threads vs. Processes

A Thread is the fundamental unit of CPU utilization. It represents an independent thread of execution within a parent process.

User-Level Threads (ULT) vs. Kernel-Level Threads (KLT):

  • User-Level Threads (Many-to-One Model): Managed completely by user-space runtime thread library (e.g., Green threads). Kernel is completely unaware of thread existence. Switching threads does not require kernel mode trap.
    Flaw: If one ULT makes a blocking system call (e.g., disk read), the entire process and all peer threads block! Cannot run in parallel on multicore CPUs.
  • Kernel-Level Threads (One-to-One Model): Supported and scheduled directly by the OS kernel (e.g., Linux pthreads, Windows threads). Each user thread maps to a distinct kernel thread. True multicore hardware parallelism; if one thread blocks, others continue executing. Modern standard.

9.2 Inter-Process Communication (IPC) Mechanisms

Because processes run in isolated address spaces, they must use explicit IPC mechanisms to exchange data:

  1. Ordinary Pipes: Unidirectional byte stream for parent-child processes. Controlled via file descriptors fd[0] (read) and fd[1] (write). Exists only while processes live.
  2. Named Pipes (FIFOs): Bidirectional pipe with a directory entry on disk (mkfifo). Unrelated processes can communicate by opening the FIFO file.
  3. Shared Memory: Fastest IPC mechanism. OS maps a common physical memory region into the virtual address spaces of both processes. Processes read and write at raw RAM bus speed without kernel intervention (requires semaphores to coordinate access).
  4. Message Queues: Kernel-managed linked list of messages. Processes deposit and retrieve structured messages. Asynchronous and safe, but requires kernel mode transitions.
  5. Network Sockets: Endpoint communication across network boundaries (TCP/IP) or local loopback (UNIX Domain Sockets). Universal for microservices and distributed systems.

9.3 Linux File System Architecture & Inodes

The Linux Virtual File System (VFS) abstracts all physical storage devices as files ("Everything is a file" philosophy):

  • Superblock: Stores metadata about the overall filesystem (filesystem type, size, total block count, free block count, mount status).
  • Inode (Index Node): The fundamental metadata record for an individual file. Stores:
    • File type and permissions (rwxr-xr-x).
    • Owner User ID (UID) and Group ID (GID).
    • File size in bytes.
    • Timestamps: Access time (atime), Modification time (mtime), Change time (ctime).
    • Direct and Indirect Block Pointers pointing to actual data blocks on disk.
    • Crucial Note: The Inode does NOT store the file name! Directory entries map file names to Inode numbers.
  • Hard Link vs. Soft (Symbolic) Link:
    • Hard Link: An additional directory entry pointing to the exact same Inode. Deleting the original file does not delete the data until all hard links (link count $== 0$) are removed. Cannot link across different filesystems.
    • Soft Link (Symlink): A unique file with its own distinct Inode whose data block contains the string path of the target file. If original file is deleted, the symlink becomes a dangling/broken link. Works across filesystems.

9.4 Disk Scheduling Algorithms

Minimizes mechanical disk head movement (Seek Time) on traditional Hard Disk Drives (HDDs):

  • First-Come First-Served (FCFS): Requests serviced in order of arrival. Simple, but incurs massive head swings across the disk platters.
  • Shortest Seek Time First (SSTF): Selects the request with the minimum seek time from the current head position. Minimizes average seek time, but causes Starvation for requests at extreme cylinder edges.
  • SCAN (Elevator Algorithm): Disk arm moves in one direction servicing all requests until it hits the end cylinder of the disk, then reverses direction servicing requests on the way back. Eliminates starvation.
  • C-SCAN (Circular SCAN): Moves in one direction servicing requests until reaching the end, then immediately returns to the beginning of the disk without servicing requests on the return trip. Provides uniform waiting time.
  • LOOK and C-LOOK: Practical variants of SCAN and C-SCAN. The arm moves only as far as the final request in each direction, reversing without going all the way to the physical boundary cylinder of the disk.

9.5 Top 30 High-Frequency Placement Interview Questions

Q1: What is the main difference between a process and a thread?

A process is an isolated program in execution with its own virtual address space, PCB, and resources. A thread is an execution unit within a process sharing the code, data, and heap segments, while maintaining its own private stack, registers, and program counter.

Q2: What happens during a Context Switch?

The OS saves the CPU registers, program counter, and stack pointer of the active process into its PCB in kernel memory, updates its state to Ready or Waiting, selects another process from the Ready Queue, switches memory page table registers (CR3), and restores the saved registers of the new process.

Q3: Why is Peterson's Algorithm not sufficient on modern hardware?

Modern multi-core processors use instruction pipelining, speculative execution, out-of-order execution, and store buffers, which can reorder read/write operations on memory, breaking software-only synchronization assumptions unless hardware memory fences/barriers are used.

Q4: What is Belady's Anomaly and which algorithms exhibit it?

Belady's Anomaly is the phenomenon where increasing the number of physical page frames allocated to a process paradoxically results in an increase in the number of page faults. It occurs in FIFO page replacement, but cannot occur in stack-based algorithms like LRU or Optimal.

Q5: What are Coffman's four conditions for deadlock?

Mutual Exclusion, Hold and Wait, No Preemption, and Circular Wait. Deadlock can arise if and only if all four conditions hold simultaneously.

Q6: How does Copy-On-Write (COW) optimize fork()?

During fork(), instead of duplicating physical RAM pages, the kernel shares pages between parent and child marked as read-only. When either process attempts to write, a page fault triggers the OS to duplicate that single page in RAM, saving immense CPU time and memory.

Q7: What is Thrashing and how can the OS resolve it?

Thrashing occurs when a process spends more time paging data between RAM and swap disk than executing instructions, collapsing CPU utilization. It is resolved using the Working Set Model by ensuring processes receive their complete working set of frames, or by suspending processes to reduce multiprogramming degree.

Q8: Differentiate between Internal and External Fragmentation.

Internal fragmentation occurs when allocated memory blocks exceed the memory requested by the process, wasting space inside the partition (common in Fixed Partitioning and Paging). External fragmentation occurs when total free memory is adequate but broken into non-contiguous scattered holes (common in Variable Partitioning and Segmentation).

Q11: What is the exact difference between a Process and a Thread?

A Process is an executing instance of a program with its own isolated address space (Text, Data, BSS, Heap, Stack) and Process Control Block (PCB). A Thread (Lightweight Process / LWP) is a basic unit of CPU utilization within a process; threads share the parent process's code section, data section, heap, and open OS resources (file descriptors), but maintain their own independent Program Counter, registers, and Stack in a Thread Control Block (TCB). Context switching between threads is an order of magnitude faster because page tables and TLB caches remain valid.

Q12: What is Priority Inversion and how does Priority Inheritance solve it?

Priority Inversion occurs when a high-priority process ($P_H$) is blocked waiting for a shared lock held by a low-priority process ($P_L$), and a medium-priority process ($P_M$) preempts $P_L$, indirectly starving $P_H$. The Priority Inheritance Protocol (PIP) resolves this by dynamically boosting $P_L$'s priority to match $P_H$'s until $P_L$ releases the critical resource, preventing $P_M$ from preempting it.

Q13: Compare Disk Scheduling Algorithms: SSTF vs SCAN vs C-SCAN vs C-LOOK.

Shortest Seek Time First (SSTF) serves requests closest to current head position, but risks starvation of outer tracks. SCAN (Elevator algorithm) sweeps across the disk from one end to the other, serving requests in its path, then reverses. C-SCAN (Circular SCAN) sweeps in only one direction, then immediately returns to the start without serving requests on the return trip, providing uniform wait times. C-LOOK optimizes C-SCAN by only traveling as far as the final request in each direction rather than traversing all the way to the physical disk platter edge.

Q14: How does a UNIX Inode structure allocate blocks for large files?

A standard UNIX Inode contains 12 direct block pointers (pointing directly to data blocks for small files), 1 single indirect pointer (points to a disk block containing addresses of data blocks), 1 double indirect pointer (points to a block of indirect pointers), and 1 triple indirect pointer. This hierarchical multi-level index allows fast $O(1)$ access for small files while supporting multi-terabyte files without external fragmentation.
