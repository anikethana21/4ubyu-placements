Operating System Foundations, Architecture & Process Memory Layout

Source Video: OS Core Concepts Explained | Part 1 • Instructor: Vivek Gupta (Ex-Google, AlgoZenith) • Timeline: 00:00:00 – 00:48:30

Core Takeaway for Technical Interviews

An Operating System is not just a resource allocator; it is a hardware virtualizer and isolation engine. Interviewers at Google, Microsoft, and Amazon routinely evaluate candidate clarity on the precise boundary between User Space and Kernel Space, the hardware mechanics of System Calls, and the exact virtual memory segmentation of an executing binary.

1.1 The Operating System as a Hardware Mediator

At bare metal, a computer system consists of raw electronic hardware: the Central Processing Unit (CPU), Physical Memory (DRAM), and Peripheral I/O Devices (NVMe SSDs, NICs, keyboards). Without an operating system, every user program would need to interface directly with hardware registers, issue raw memory bus commands, and manage physical cylinder sectors on storage media.

The Operating System solves this by functioning as:

  • Resource Allocator: Mediates conflicting hardware requests from multiple concurrently running tasks, ensuring fair access, high utilization, and deadlock prevention.
  • Extended Machine / Abstraction Layer: Hides device-specific low-level complexity (e.g., AHCI/NVMe protocol registers) behind clean, uniform APIs such as standard POSIX file operations (open, read, write, close).
  • Protection and Security Arbiter: Enforces memory boundaries, preventing Rogue Process A from reading or modifying the address space of Process B or corrupting the OS kernel itself.

1.2 Dual-Mode Operation & Hardware Protection

To prevent malicious or buggy applications from halting the CPU or overwriting critical memory structures, modern x86-64 and ARM processors implement hardware-enforced execution privilege levels (Hierarchical Protection Domains, often known as Rings):

  • User Mode (Ring 3): Mode bit set to 1. The CPU restricts access to privileged machine instructions. User applications cannot directly disable interrupts, alter page tables, or perform raw I/O port writes. Attempting to execute a privileged instruction in User Mode immediately triggers a hardware general-protection fault trap.
  • Kernel / Supervisor Mode (Ring 0): Mode bit set to 0. The CPU allows unrestricted execution of all machine instructions, direct hardware port access, and full control over system control registers (such as CR0, CR3 for page table roots on x86).

The System Call Execution Pipeline

When a user-space application requires hardware access (e.g., printing to terminal or reading a disk block), it cannot execute it directly. It must execute a System Call via a software interrupt or specialized machine instruction (⏱️ 48:30):

  1. The user process places system call arguments in designated CPU registers (e.g., on Linux x86-64: RAX holds the system call number, while RDI, RSI, RDX hold parameters).
  2. The process executes the syscall (or legacy int 0x80) instruction.
  3. The CPU hardware saves user program counter (RIP) and stack pointer (RSP), flips the hardware Mode Bit from 1 (User) to 0 (Kernel), and vectors control to the predefined System Call Table in kernel memory.
  4. The kernel inspects RAX, dispatches the corresponding handler function (e.g., sys_read()), verifies user buffer pointers for memory safety, and performs the operation.
  5. Upon completion, the kernel writes the return code into RAX and executes sysret, switching the mode bit back to User Mode (1) and restoring user execution context.

1.3 Program vs. Process: Architectural Distinctions

In placement interviews, candidates often confuse programs with processes (⏱️ 13:01):

Attribute Program Process
Nature Passive entity stored on disk (e.g., compiled ELF binary /usr/bin/ls). Active runtime entity loaded into main memory with allocated CPU cycles.
Lifespan Permanent until deleted from secondary storage. Dynamic; created upon launch, exists through state transitions, destroyed upon termination.
Resource Footprint Consumes only disk storage space. Allocates RAM, CPU registers, stack/heap, file descriptors, and kernel PCB structures.
Relationship One program can spawn multiple distinct processes (e.g., opening 4 separate terminal windows). Each process has its own isolated virtual address space and PID.

1.4 Process Control Block (PCB): The Process Metadata Core

The Operating System represents each process internally using a kernel data structure known as the Process Control Block (PCB) (in the Linux kernel, represented by struct task_struct) (⏱️ 24:28). The PCB contains:

  • Process Identifier (PID): Unique integer identifier assigned by the kernel (e.g., PID 1 is systemd/init).
  • Process State: Current status flag (New, Ready, Running, Waiting, Terminated).
  • Program Counter (PC): Pointer storing the physical/virtual address of the next machine instruction to be executed by the CPU.
  • CPU Registers: Snapshot of all hardware registers (Accumulator, Index, Stack Pointer RSP, Base Pointer RBP, Flags register) saved whenever the process is preempted.
  • Memory Management Information: Base and limit register values, or pointers to the top-level Page Table (e.g., CR3 register value in x86).
  • Accounting & Scheduling Attributes: CPU priority, time slice remaining, CPU time consumed, waiting time accumulated.
  • I/O Status & Open Files: File Descriptor Table (FDT) mapping index integers (0: stdin, 1: stdout, 2: stderr) to kernel file pointers.

1.5 Process Memory Layout (Virtual Address Space Anatomy)

When the OS loads a program into memory, it assigns it a contiguous-looking private virtual address space divided into 4 primary functional segments (⏱️ 33:49):

graph TD HighAddr["High Address: 0x7FFFFFFFFFFF"] Stack["Stack Segment (Downwards growth: Local vars, frame pointers)"] Gap["Unallocated Free Address Space"] Heap["Heap Segment (Upwards growth: malloc, dynamic objects)"] BSS["BSS Segment (Uninitialized globals/statics zeroed)"] Data["Data Segment (Initialized globals/statics)"] Text["Text / Code Segment (Machine instructions: Read-Only)"] LowAddr["Low Address: 0x000000000000"] HighAddr --- Stack Stack --> Gap Gap --- Heap Heap --- BSS BSS --- Data Data --- Text Text --- LowAddr
  1. Text (Code) Segment:
    • Contains the raw compiled executable machine code instructions.
    • Read-Only Protection: Hardware-enforced read-only permission flag to prevent self-modifying code or buffer overflow exploits from altering program logic.
    • Sharable: Multiple concurrent processes executing the same binary (e.g., 10 instances of bash) can safely share the single physical copy of the text segment in RAM.
  2. Data Segment (Initialized Data & BSS):
    • .data: Stores global and static variables explicitly initialized with non-zero values (e.g., int max_users = 500;).
    • .bss (Block Started by Symbol): Stores uninitialized or zero-initialized global and static variables (e.g., static int buffer[1024];). Does not consume binary file space on disk; kernel automatically zero-fills this space upon process instantiation.
  3. Heap Segment:
    • Allocated dynamically at runtime via library calls such as malloc(), calloc(), realloc() in C, or new in C++.
    • Grows upwards toward higher memory addresses. Managed by runtime allocators (e.g., ptmalloc, jemalloc) which invoke kernel system calls brk() or mmap() when expanding.
  4. Stack Segment:
    • Stores activation records (stack frames) for active function calls.
    • Contains function parameters, local automatic variables, caller return addresses, and saved register frames.
    • Grows downwards toward lower memory addresses. Managed automatically by CPU hardware via Stack Pointer (RSP) and Base Pointer (RBP). If stack and heap collide without sufficient address space, a Stack Overflow occurs.
