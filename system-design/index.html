System Design Fundamentals & Scaling

High Availability • L4/L7 Routing

🏛️ Architectural Evolution: From Single Node to Planetary Scale

Every web service begins as a monolithic process paired with a co-located relational database. Scaling becomes necessary when traffic, storage, or compute bounds exceed single-machine limits. We analyze the two core vectors of scaling:

Dimension Vertical Scaling (Scale-Up) Horizontal Scaling (Scale-Out)
Mechanism Add more RAM, faster NVMe SSDs, or 128-core CPUs to existing server. Add more commodity machines behind an intelligent Load Balancer.
Hard Limit Bounded by hardware physical limits and hyper-exponential cost curves. Virtually unbounded linearly with distributed coordination.
Downtime Requires maintenance reboot to upgrade physical chips. Zero downtime via blue-green / rolling fleet deployment.
Fault Tolerance Single Point of Failure (SPOF). Hardware death crashes whole company. Resilient against machine, rack, and whole availability-zone outages.

⚖️ Load Balancer Deep-Dive: Layer 4 vs Layer 7

Layer 4 (Transport Level): Inspects IP address and TCP/UDP port without terminating TLS or reading HTTP payloads. Operates at wire-speed ($>10 ext{M}$ packets/sec) using Linux IPVS (IP Virtual Server) or AWS NLB.

Layer 7 (Application Level): Terminates TLS, decrypts packets, inspects HTTP headers, cookies, URL paths, and query parameters. Routes /api/checkout to checkout microservice and /api/feed to caching clusters.

Database Sharding, Replication & CAP Theorem

Distributed Storage • Consistency

📦 Horizontal Partitioning: Database Sharding Strategies

When a database table grows to hundreds of millions of rows, index B-Trees exceed memory and disk I/O thrashes. Sharding splits the dataset across distinct physical database servers:

Sharding Strategy How it Works Pros & Cons
Range-Based Partition by key intervals (e.g., User IDs 1–1M $ o$ Shard A, 1M–2M $ o$ Shard B). Simple range scans; severe hotspot risk for sequential auto-increment keys.
Hash-Based Apply uniform hash $shard = hash(user\_id) \pmod N$. Uniform distribution; difficult to add nodes without massive data migrations.
Directory-Based Lookup service stores dynamic mapping of key $ o$ shard ID in high-speed Redis. Maximum flexibility; adds extra network hop and single point of failure.

🌐 The CAP & PACELC Theorem Invariants

The CAP Theorem (Eric Brewer) proves that under a network partition ($P$), a distributed datastore can guarantee at most one of:

  • Consistency ($C$): Every read receives the most recent write or an explicit error (CP Systems: HBase, Spanner, Zookeeper).
  • Availability ($A$): Every non-failing node returns a non-error response, but without guarantee of latest data (AP Systems: Cassandra, DynamoDB, Couchbase).
PACELC Generalization (Daniel Abadi):
If there is a Partition ($P$), how does the system choose between Availability ($A$) and Consistency ($C$); Else ($E$), when running normally without partitions, how does it balance Latency ($L$) and Consistency ($C$)?
Examples: MongoDB is PC/EC (consistency prioritized always). DynamoDB is PA/EL (availability and low latency prioritized).

Event Sourcing Architecture

Immutable Ledger • Audit Trails

📜 Beyond CRUD: Storing Delta Events as the Single Source of Truth

Traditional CRUD databases perform in-place mutation (UPDATE accounts SET balance = balance - 100). The historical context of why and how the state reached this number is permanently lost. Event Sourcing treats every change as an immutable state-transition event appended to an append-only journal:

// Append-Only Event Log Stream: Account-9481
[
  { "id": 1, "type": "AccountOpened", "ts": 1700000000, "data": { "owner": "Aniket", "balance": 0 } },
  { "id": 2, "type": "MoneyDeposited", "ts": 1700000120, "data": { "amount": 1000 } },
  { "id": 3, "type": "FraudHoldApplied", "ts": 1700000240, "data": { "reason": "Unusual IP" } },
  { "id": 4, "type": "MoneyWithdrawalAttempted", "ts": 1700000300, "data": { "amount": 200 } }
]

⚡ Replayability, Time-Travel & Snapshots

Current balance is simply derived by reducing the event stream from $t_0$ to $t_{now}$: $ ext{State}(t) = \sum_{i=1}^t ext{Event}_i$.

Snapshots: To prevent replaying millions of historical events on cold start, a periodic worker writes a checkpoint snapshot every 1,000 events. Read operations load the latest snapshot and replay only subsequent events.

CQRS (Command Query Responsibility Segregation)

Read/Write Decoupling • Projections

✂️ Separating the Write Model from the Read Model

In high-scale systems, write operations have completely different scaling vectors than read operations. Writes require transactional validation, locking, and strict consistency. Reads require denormalized, fast sub-millisecond aggregations.

graph TD Client([Client App]) -->|Command: POST /orders| API_Write[Write Gateway] Client -->|Query: GET /orders?user=123| API_Read[Read Gateway] API_Write --> DB_Write[(Postgres / EventStore - Write Model)] DB_Write --> Stream[CDC / Kafka Event Bus] Stream --> Worker[Projection Materializer] Worker --> DB_Read[(Elasticsearch / Redis - Read Model)] API_Read --> DB_Read
Key Benefit of CQRS: You can optimize your read database with zero joins using fully denormalized JSON in Elasticsearch or MongoDB, while keeping your write database in 3rd Normal Form (3NF) in PostgreSQL with row-level locks.

Rate Limiting Algorithms & Distributed Architecture

Piyush Garg Lecture CVItTb_jdkE • Defense in Depth

🛡️ Why Rate Limiting is Mandatory

Rate limiting protects servers from Denial of Service (DoS) attacks, brute-force credential stuffing, API resource starvation, and cascading failures across microservices. It responds with HTTP status 429 Too Many Requests and headers Retry-After and X-RateLimit-Remaining.

🔬 The 5 Core Rate Limiting Algorithms Compared

Algorithm Core Mechanism Pros Cons
Token Bucket Tokens refilled at rate $R$ up to capacity $C$. Each request consumes 1 token. Allows controlled traffic bursts; memory efficient (2 variables: count & last_timestamp). Tuning parameters $R$ and $C$ can be challenging across diverse API endpoints.
Leaky Bucket FIFO queue of capacity $B$. Requests enter queue; process at steady constant rate $O$. Smooths out bursts; guarantees constant outbound processing rate. Bursts are delayed; requests dropped if queue fills up, causing high queueing latency.
Fixed Window Counter Time sliced into fixed 60s windows. Counter resets at start of each window. Simplest to implement; minimal memory usage. Boundary Burst Vulnerability: $2 imes$ limit can pass at window transition edge.
Sliding Window Log Keep timestamp of every request in sorted set (Redis ZSET). Prune timestamps older than window. Mathematically 100% accurate; eliminates boundary burst issue. Memory Exhaustion: Storing every timestamp consumes enormous RAM under heavy traffic.
Sliding Window Counter Hybrid approximation: $ ext{Count} = ext{CurrentWindowCount} + ext{PrevWindowCount} imes (1 - ext{OverlapRatio})$. Memory efficient (only 2 numbers); smooths boundary spikes with 99.9% accuracy. Assumes requests in previous window were uniformly distributed.

💻 Production Redis Sliding Window Rate Limiter (Atomic Lua Script)

To eliminate race conditions across multiple distributed application nodes, rate checking must execute atomically inside Redis using a Lua script:

-- KEYS[1]: User or IP Rate Limit Key (e.g. "rate:user_9481")
-- ARGV[1]: Current Unix Timestamp in milliseconds
-- ARGV[2]: Window Size in milliseconds (e.g. 60000 for 1 minute)
-- ARGV[3]: Max Allowed Requests (e.g. 100)

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clearBefore = now - window

-- 1. Remove all requests older than the rolling window
redis.call('ZREMRANGEBYSCORE', key, 0, clearBefore)

-- 2. Count requests currently in window
local currentRequests = redis.call('ZCARD', key)

-- 3. Check threshold
if currentRequests < limit then
    -- Add current request timestamp to sorted set
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, math.ceil(window / 1000))
    return {1, limit - currentRequests - 1} -- Allowed: {status=1, remaining}
else
    return {0, 0} -- Blocked: {status=0, remaining=0}
end

Consistent Hashing & Virtual Nodes

Piyush Garg Lecture IC5Y1EE-aj4 • Distributed Sharding

🎯 The Classic Modulo Rehashing Disaster

Traditional horizontal sharding maps keys to servers using $server = hash(key) \pmod N$. When one server dies or a new server is added ($N o N+1$), almost 100% of keys map to completely different servers. All caches are invalidated simultaneously, causing a catastrophic Cache Avalanche that melts backend databases.

🔄 The Circular Hash Ring Solution

Consistent Hashing maps both servers and keys onto an abstract 32-bit circular hash space ($0$ to $2^{32} - 1$):

  • Hash server IPs onto points on the ring: $hash("10.0.0.1"), hash("10.0.0.2")$.
  • Hash incoming request keys onto points on the ring: $hash("user\_profile\_91")$.
  • Walk clockwise from the key's position until the first server node is encountered.
  • When server $N$ is removed, only keys residing between $N-1$ and $N$ are remapped to $N+1$. On average, only $ rac{1}{N}$ fraction of keys move!
The Non-Uniformity Problem & Virtual Nodes (v-nodes):
With few physical servers, hash distribution is uneven, leading to severe server hotspots. Solution: Assign each physical node 100–300 "Virtual Nodes" scattered across the ring (e.g., NodeA-vn1, NodeA-vn2, NodeA-vn3). This guarantees near-perfect uniform distribution with standard deviation $< 5\%$.

Distributed Video Streaming at Scale (YouTube & Netflix)

Piyush Garg Lecture -JtjQ-OA7XE • Adaptive Bitrate

📹 Why Standard MP4 Progressive Download Fails at Scale

Sending a raw .mp4 file over HTTP breaks down on mobile networks: if a user on 3G starts playing a 4K video, the player buffers for 20 seconds. If the user leaves after 10 seconds, gigabytes of downloaded data are completely wasted. Furthermore, progressive downloads cannot dynamically adjust video resolution when network bandwidth fluctuates.

⚡ Adaptive Bitrate Streaming (ABR): HLS & MPEG-DASH

Adaptive Bitrate Streaming slices video into tiny independent chunks (typically 2 to 6 seconds duration) and encodes each chunk into multiple resolution/bitrate tiers (1080p @ 5Mbps, 720p @ 2.5Mbps, 480p @ 1Mbps, 360p @ 500kbps):

graph LR Source[Raw 4K Video Upload] --> Queue[Kafka / SQS Ingest Queue] Queue --> Transcoder[FFmpeg GPU Transcoding Cluster] Transcoder --> Chunks1[1080p 4s Chunks .ts] Transcoder --> Chunks2[720p 4s Chunks .ts] Transcoder --> Chunks3[360p 4s Chunks .ts] Transcoder --> Manifest[Master Playlist .m3u8] Chunks1 & Chunks2 & Chunks3 & Manifest --> S3[(AWS S3 Storage)] S3 --> CDN[Global Edge CDN Cloudflare / Fastly] CDN --> Client[ExoPlayer / HLS.js Client]

# EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080,CODECS="avc1.640028,mp4a.40.2"

# EXT-X-STREAM-INF:BANDWIDTH=2500000,RESOLUTION=1280x720,CODECS="avc1.4d401f,mp4a.40.2"

# EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360,CODECS="avc1.42e01e,mp4a.40.2"

chunk_002.ts
# EXTINF:4.000,
chunk_003.ts
Client-Side Heuristic Algorithm: The video player (Video.js, Shaka Player) continuously measures the download time of chunk $N$. If the network speeds up, the player fetches chunk $N+1$ from the 1080p stream. If the user enters an elevator, the player seamlessly drops to chunk $N+1$ from the 360p stream without a single millisecond of buffering.

High-Scale UPI & Distributed Payment Processing

Piyush Garg Lecture fqySz1Me2pI • Idempotency & Sagas

💳 Anatomy of a 100,000 TPS Payment Switch

Processing financial transactions requires absolute correctness, zero phantom double-debits, and high fault tolerance across banks whose core banking servers (CBS) frequently drop connections.

🔑 Strict Idempotency Implementation

Every payment request must mandate an Idempotency-Key in the HTTP request headers (UUIDv4 generated on the client device before network transit). The payment gateway stores this key in a distributed lock / table before processing:

// Payment Processing Pseudo-Code with Redis Atomic Lock
async function processPayment(idempotencyKey, amount, fromAccount, toAccount) {
    // 1. Try acquiring unique lock in Redis for 120 seconds
    const acquired = await redis.set(`idem:${idempotencyKey}`, "PROCESSING", "NX", "EX", 120);
    if (!acquired) {
        // If already exists, return previous cached transaction result or "IN_PROGRESS"
        const existingStatus = await redis.get(`idem:${idempotencyKey}`);
        return { status: existingStatus, message: "Duplicate transaction prevented" };
    }

    try {
        // 2. Execute Distributed Transaction via Saga Orchestrator
        const result = await sagaOrchestrator.executeTransfer(fromAccount, toAccount, amount);
        await redis.set(`idem:${idempotencyKey}`, JSON.stringify(result), "EX", 86400);
        return result;
    } catch (err) {
        await redis.del(`idem:${idempotencyKey}`); // Release on recoverable failure
        throw err;
    }
}

Bloom Filters & Probabilistic Data Structures

Piyush Garg Lecture vz0QUa4CS3o • Fast Negative Lookups

🎲 The Space-Efficient Membership Query

A Bloom Filter is a space-efficient probabilistic data structure used to test whether an element is a member of a set. It answers with two possible guarantees:

  • "Definitely NOT in set" → 100% Guaranteed Correct. Zero False Negatives.
  • "POSSIBLY in set" → High probability of being in set, but with small configurable False Positive probability ($p$).

📐 Mathematical Formulations

Given bit array size $m$, expected number of items $n$, and $k$ independent hash functions:

  • Optimal Number of Hash Functions: $k = rac{m}{n} \ln 2 pprox 0.7 imes rac{m}{n}$
  • False Positive Probability ($p$): $p pprox \left(1 - e^{-kn/m} ight)^k$
  • Required Bits per Element: For $1\%$ false positive rate ($p = 0.01$), you need approximately $9.6$ bits per element regardless of whether the element is a 1KB string or 100MB file!
Production Use Cases: Google Chrome checks malicious URLs against a local Bloom filter before querying servers. Apache Cassandra uses Bloom filters on each SSTable file to avoid expensive disk seeks for non-existent row keys.

Real-Time Multi-Party Video Calls (WebRTC, SFU, MCU)

Piyush Garg Lecture Zaz6hYVm-WE • Real-Time Media

📡 The 3 Multi-Party Video Call Topologies

Architecture How Media Flows Client Bandwidth Server Cost Max Scale
Full Mesh (P2P) Each client sends video directly to every other participant via WebRTC peer connection. $O(N)$ uplink and downlink. Crushes client on $N > 4$. $0$ Media Servers (only STUN/TURN for NAT traversal). 2–4 participants.
MCU (Multipoint Control Unit) Clients send 1 stream to server; server decodes, composites video into 1 grid, re-encodes, and sends 1 stream back. $O(1)$ uplink and downlink (extremely lightweight for client). Hyper-expensive GPU/CPU transcoding per active call. Bounded by server rendering latency ($100$–$200$ms delay).
SFU (Selective Forwarding Unit) Client sends 1 stream to server; server acts as intelligent router and forwards streams to participants without transcoding. $1$ uplink stream, $N-1$ downlink streams (Simulcast optimization). Low CPU usage (pure network routing with zero transcoding). Industry Standard: Scales to 500+ users (used by Zoom, Google Meet, Discord).

Gossip Protocol & Distributed Cluster Membership

Piyush Garg Lecture TUc_hPtxyf8 • P2P Consensus

🗣️ Decentralized Epidemic State Synchronization

In massive clusters of 10,000+ nodes (such as Apache Cassandra, Amazon DynamoDB, or Consul), having a centralized coordinator creates an extreme bottleneck and single point of failure. The Gossip Protocol uses randomized peer-to-peer message exchanges to propagate node states:

  • Every $T$ seconds (e.g. 1s), each node picks $k$ random peers (typically $k = 3$) from its membership table.
  • The node transmits its heartbeat counter and status list to those $k$ peers.
  • Receiving nodes update their local tables if the incoming heartbeat generation is higher.
  • Convergence Guarantee: Information disseminates exponentially like an epidemic, reaching all $N$ nodes in $O(\log N)$ time with high probability!

💓 Phi-Accrual Failure Detection

Traditional heartbeats use binary threshold (e.g., if no ping in 5 seconds $ o$ declare dead). In real networks with transient packet jitter, this causes false alarms. $\Phi$-Accrual Failure Detectors output a continuous suspicion level $\Phi = -\log_{10}(P_{ ext{later}}(t - t_{ ext{last}}))$ based on historical heartbeat arrival distributions.

Distributed Message Queues & Event Streaming

Piyush Garg Lecture 2tCfITBVKjA • Kafka vs RabbitMQ

📬 Smart Broker vs Distributed Commit Log

Characteristic RabbitMQ (AMQP Message Broker) Apache Kafka (Distributed Commit Log)
Model Smart Broker, Dumb Consumer. Broker tracks message ACKs and delivery states. Dumb Broker, Smart Consumer. Broker writes append-only log; consumers track their own offsets.
Message Retention Messages are deleted from broker immediately upon consumer ACK. Messages persist for configured retention period (e.g. 7 days); can be replayed infinitely.
Ordering Guarantee Ordered within a single queue, but concurrency hurts ordering. Strictly ordered per Partition; keys determine partition destination.
Throughput Tens of thousands of msgs/sec. Millions of msgs/sec via sequential disk writes and Zero-Copy OS sendfile.

Resilient Microservice Patterns (Saga, Outbox, Bulkhead)

Piyush Garg Lecture OdNpY3WQniQ • Fault Tolerance

🔌 The Circuit Breaker State Machine

Prevents cascading failures when downstream services experience outages or elevated latencies:

  • Closed: Normal operation. All requests pass through. Error counts tracked.
  • Open: Failure threshold exceeded (e.g., $50\%$ errors over 10s). Requests fail immediately with fallback response without hitting downstream.
  • Half-Open: After cooldown timeout (e.g., 30s), a limited trial batch of requests is allowed through to test downstream health. If successful, resets to Closed; otherwise returns to Open.

📦 The Transactional Outbox Pattern

Solves the dual-write problem (writing to a database AND publishing to a message broker). An application writes business entities and outbound events inside a single local database transaction. A Change Data Capture (CDC) engine (e.g., Debezium) tails the WAL and streams events to Kafka with zero message loss.

Top 20 System Design Technical Interview Questions

FAANG • High Frequency Architecture Cases
Click any question card to reveal the architectural blueprint, component design, back-of-the-envelope calculations, and interviewer trap questions.
Q01 Design a Distributed Rate Limiter for an API Gateway
High Scale ▼

Core Strategy: Use the Sliding Window Counter or Token Bucket algorithm backed by a Redis Cluster. To prevent concurrency race conditions where multiple requests pass concurrently, use an atomic Lua script executed directly on the Redis engine.

Key Components: API Gateway (Envoy / Kong), Redis Cluster partitioned by client IP or API token, Local In-Memory Fallback Cache if Redis suffers temporary latency spikes.

Interviewer Trap: "What happens when your centralized Redis cluster experiences network partitions?"
Answer: Fall back to local in-memory token bucket on each API Gateway node with relaxed limits (Soft Limiting) to prioritize availability over strict global synchronization.

Q02 Design YouTube / Netflix Video Streaming at Planetary Scale
Media Pipeline ▼

Core Strategy: Split raw uploaded video into 4-second chunks using distributed worker queues (Kafka + FFmpeg on GPU instances). Transcode into multiple bitrates (1080p, 720p, 480p, 360p) in HLS (.m3u8 + .ts chunks). Serve video chunks via geographically distributed Edge CDNs (Cloudflare / Fastly).

Bandwidth Optimization: $95\%$ of video traffic is served directly from CDN caches. Client players dynamically switch bitrates based on live TCP buffer fullness measurements.

Q03 Design a High-Throughput URL Shortener (TinyURL)
Classic System ▼

Core Strategy: Use Base62 encoding ($[0-9, a-z, A-Z]$) over a 64-bit integer ID. A 7-character Base62 string yields $62^7 pprox 3.5 ext{ Trillion}$ unique URLs. To prevent ID collision across distributed nodes without centralized lock contention, use a Token Range Service (Zookeeper allocates $1 ext{M}$ ID ranges to each server instance).

HTTP Redirect Choice: Use HTTP 302 Found (Temporary Redirect) if analytics/click-tracking are required on every hit; use HTTP 301 Moved Permanently to let browser cache redirect and reduce backend load.

Q04 Design WhatsApp / Real-Time Chat System
WebSockets ▼

Core Strategy: Maintain persistent full-duplex WebSocket connections between client apps and a stateful Gateway cluster. A distributed Session Service (Redis) tracks which Gateway server hosts which active user_id connection. When User A messages User B, the server publishes to User B's gateway via Redis Pub/Sub.

Offline Messages: If User B is disconnected, store unread messages in Cassandra or ScyllaDB (partitioned by recipient ID) and send a push notification (FCM/APNS). When User B reconnects, drain the pending queue and issue delivery receipts.

Q05 Design a Distributed In-Memory Cache (Redis / Memcached)
Caching ▼

Core Strategy: Distribute keys across nodes using Consistent Hashing with Virtual Nodes. Use an $O(1)$ LRU (Least Recently Used) eviction policy constructed from a Doubly Linked List paired with a Hash Map.

Preventing Cache Stampede (Thundering Herd): When a hot key expires and 10,000 QPS query simultaneously, use Mutex Locking (single thread fetches from DB while others wait) or Probabilistic Early Expiration (XFetch).

Q06 Design Twitter / X News Feed System
Feed Generation ▼

Fan-out on Write (Push Model): When User A tweets, append tweet ID to the Redis timeline list of all followers. Fast reads ($O(1)$); terrible for celebrities with 100M followers (takes 5 minutes to write 100M records).

Hybrid Solution: Normal users use Fan-out on Write. Celebrity tweets (e.g. $>20 ext{k}$ followers) use Fan-out on Read: when a follower opens Twitter, the app dynamically merges the pre-computed feed with the celebrity's recent tweets.
